# 美术把关怎么做

为什么有这一页：所有者 2026-11-21 定，画面是第一要素，视觉 PR 没有「美术通过」不合；同一天又说「T00 的 art 标准要沉淀下来，同步给 T05 用」。这一页是把那一天审出来的判法写成能直接拿来用的条目。每次暂不通过的原因和改法，一条一行记在 [`docs/ART-LESSONS.md`](../../docs/ART-LESSONS.md)。T00 现有画面的毛病和先后在 [`docs/ART-REVIEW.md`](../../docs/ART-REVIEW.md)。

## 一、开工先做

1. 读规范：`docs/ART-SPEC.md`；审哪一关就读那一关的美术页（T05 是 `docs/t05/ART.md`）和它的目标图（`refs/` 下，旁边的 README 写着每张取什么、不取什么）。
2. 读 PR 的验收标准和作者交的图，记下提交号。
   先问「以哪张设定图、目标图为准」：查 issue 里所有者最后一次给的是哪一版，和 `refs/` 里的是不是同一张；不是，先请主创把新的放进 `refs/`。（#469：`refs/monk-apose-sheet.png` 是闭眼的第一版，所有者后来给的四视图是睁眼的，审图差点把睁眼判成走样。）
3. **下结论前把 PR 上所有人的评论和发给你的消息读完。** 作者或主创点名请你看的那一处，先看它。（#474：主创专门请看 `cam06` 的中景，审图写完「通过」才读到，改判。）
4. **自己看图，不只看作者的描述和拼图**（做法见第二节）。
5. 结论写在 PR 的评论里，第一行是「美术通过」或「美术暂不通过」（写法见第五节）。
6. 用 `send_message` 告诉三方：作者、这一关的关卡主创、总主创。

## 二、怎么看图

- **改前改后要同机位、同季节时辰、各带提交号。** 机位要能重复：`?show=<名字>`，或 `?cam=x,z,yaw,pitch`，或进页面后 `__look([眼],[看向])`。换季不重开页面，用 `__mood(season, time)`。
- **光影好坏只认 T4 的图**（`tools/gpu-render.sh`）。软件渲染（SwiftShader）的图只证明形、比例和同一渲染器下的相对关系。在评论里写明你看的是哪一种。出处：`docs/t00/art-goal.md`「每个 PR 都要做到」。
- **在预览上拍之前先问页面是哪一个提交**：`__version().commit`，每一张都打印。用 PR 评论里的**固定地址**拍，不用「最新地址」：它随推送变，一轮拍到一半会换成另一个提交（#481，十四张里前五张是 `e4e4a0d`，后九张成了 `f5435b1`）。PR 合并后预览撤掉（返回 404），那时到 canary 上看。PR 有冲突时 CI 不跑、没有预览：本地检出那个提交，`pnpm dev` 起服务再拍。
- **拍之前先核对页面真的在你要看的状态。** 脚本先打印状态钩子（`__journey()`、`__endingPass().seenBefore`、`__frame()` 这类）再截图。评审直达链接不等于你以为的状态（#483：用七印圆满的帐拍「第一次看收尾」，拍到的全是回访的样子）。
- **换作者没拍的角度。** 至少加：斜看一张、回望一张、竖屏一张；树和造像加别的季节和时辰。锁定的验收机位每张按近、中、远三带各看一遍。机位动过的，画面四边和四角各看一眼有没有新进来的东西。
- **量屏上的数，不量配方里的数。** 同一个色值在殿内的冷天光下、在暖灯下、在棚光下是三种颜色。判色只在访客实际站的光里判（第三节 3）。
- **写明没看到的。** 哪一棵树没框到、哪个提交没在预览上、哪一组只看了作者的拼图，都写进评论。
- 软件渲染很慢。T05 白盒 1280×720 一张约一分钟；T00 高档 1280×720 一张 3 到 3.5 分钟，中档 1.5 到 2.5 分钟。截图的超时设到 5 分钟以上（默认 30 秒不够）；不要用等动画帧稳定的等待（Playwright 默认的 `click` 稳定性检查），一帧要几秒。两个拍图任务同时跑会互相拖到超时，一次只跑一个。后台拍图用 `nohup`，会话重启会打断它。1600×900 在个别位置截图会超时，换 1280×720。

## 三、判法

每条写：判什么；数；在哪个机位或用什么命令量；出处。编号按加入的先后，不重排（PR 评论里已经在引用），所以组里的号不连着。数是那一次定的，换了关卡、换了光要重看它成不成立（T05 怎么用，见 `docs/ART-LESSONS.md` 末节）。

### 明暗与颜色

**1. 主体要比它的座子、背景先被看到。**
- 数：主体（脸）的屏上平均亮度 ≥ 它脚下大面（莲座）的亮度；座取脸的 0.6–0.7，背板取脸的一半上下。
- 量：造像在 `cam03`（冬，不开佛前灯），用 `tools/t05-hall.cjs` 的 `zones: true` 出每区屏上平均色。
- 出处：#407 第六轮，莲座比脸亮四分之一、面积是脸的九倍，一进门眼睛落在座上；#480 改到 0.63–0.66 后通过。压过头也不行：第七轮座压到脸的一半以下，七个座成了七个黑鼓，莲瓣读不出。
- 大像的神情在访客站的地方判：10 米外仰看、漫射光的那一张，不在平视的那一张。平视安静的脸，仰看可以是皱眉撅嘴（#480 第六轮）。有真像的照片时，把脸裁出来和我们的并排，只取「从下面看是什么样」，不照它复原颜色。

**2. 颜色的分区要落在形体的棱上，照原型图的衣式走。**
- 判：改后的正面和原型图并排，每一区的边界都在网格的棱上，没有一条直线边；该是肤的是肤，该是内衣的是内衣。
- 出处：#407 第四到六轮，胸衣是一块直边的板，露出的胸被涂成袈裟色。

**3. 颜色以屏上为准。**
- 数（T05 七佛，殿内冬光）：袈裟屏上色相 10–14°、饱和 0.40–0.50；内衣色相 125–145°、饱和 ≤ 0.27；唇用袈裟那一族的赭红（色相 12–16°，往橙褐偏），屏上亮度是脸的 0.58–0.64，饱和比脸颊高 0.10–0.15，不做大红、不做粉；描金屏上不亮过脸。
- 量：在 `cam03` 的图上按区取像素（同上）。
- 要知道的：冷的天光会把绿往青推（配方 140° 的绿，屏上是 157°），色调映射会把赭往红推（配方 11° 的赭，屏上是 5°）。配方要预偏。相邻的补色会让一个数上合格的颜色看着很艳（赭红旁边的绿），这时信数。
- 唇的那一条改过一次：我在 #407 写的是「唇的饱和不高于脸颊 0.08 以上」，它把唇压得和脸一个颜色，嘴只能靠形体的起伏和影子来读，仰看读成撅嘴。对着真像的近照（唇是一块边界清楚的朱红，嘴靠颜色读）改成上面的写法（#480 评论 7061926783）。**一个脸上的器官，要么靠颜色读，要么靠影子读；把颜色压掉，影子就来替它说话。**第七轮照「亮度 0.6–0.7、饱和高 0.15–0.2」做出来是玫瑰粉，在灰褐的脸上读成一点红，再收到现在的数（#480 评论 7062473298）。判：10 米仰看那张缩到 320 像素宽，嘴读成「深一点的嘴」，不读成「一点红」；全脸最深的是唇，不是眼上的线。
- 出处：#407 第六、七轮，#480。

**4. 阴影里要看得清，暗处不能是一块黑。**
- 数：殿内仰看梁架那一站，明度（CIE L\*）中位数 L50 ≥ 10，L95 − L05 ≥ 15，梁的层数数得出来。
- 暗处新加的构件，和旁边已有的暗面比，不单看它自己：新构件的 L50 和同一处已有的暗面一个量级，构件与构件之间差 5 个 L* 以上。（#475 `b13d87e`，审图二：山门新加的天花 L05/L50/L95 是 6.2/7.7/9.4，梁和板只差 3 个 L*，同图里门板是 8.4/12.0/15.5；构件做了，但知道有才看得见。）
- 门洞要暗（下一条）和殿内看得清是一对：一个固定的殿内亮度满足不了两头，要让它随眼睛进殿渐变。两条一起量，一起过。
- 渐变怎么量：沿中轴从门外 6 米到殿内 6 米，每 3 米朝里拍一张，量画面正中**同一块后墙**的亮度，一路升、相邻两站相差不超过一倍。不量整张图的 L50：它跟着取景变（门外那张亮的月台多，檐下那张暗的多），殿内没变暗也会掉。
- 出处：#481，为了让门洞暗把殿内补光全关，E 站 L50 5.9；第二轮把殿内天光从 0.15 调到 0.2，E 站仍只有 6.3、明度差 10.3。第五轮（`33132ef`）殿内补光随眼睛进殿升起，E 站 11.9 / 34.3，后墙五站 0.039、0.064、0.089、0.104、0.103，通过。依据是 `ART-SPEC.md` 第一条和 `t05/ART.md` CAM-05 的忌看。

**5. 门洞从外面看是暗的。**
- 数：白盒（借 T00 夏昼的雾）：远站（z = +44）门洞与墙的亮度比 ≤ 0.60，**并且**门外 6 米正对当心间 ≤ 0.25。成图（T05 自己的初冬晴冷）：远站 ≤ 0.20，门洞比直棂窗暗一半以上。
- 量：门洞取当心间门洞中间六成的面积，墙取尽间的实墙，屏上线性亮度的平均。近处那一张里看不见尽间：站在同一点转过去量实墙（这个渲染没有自动曝光，同一站点的两张图可以直接比）。门额、檐下这些自己在阴影里的面不能当分母。一张图里核对，用同一张图底部的月台铺地：门洞 ÷ 铺地 ≤ 0.35。
- **物理下限**：雾会把远处的黑抬亮。T00 夏昼的雾里，把殿内换成纯黑，44 米外也只到 0.32。所以远站的线不能定得比「纯黑时的值加一段」更低；真正判「门里暗不暗」的是不受雾影响的近处那一张。换了季时（雾薄了），远站的线要跟着收紧。
- 出处：#425 第一轮（门洞比墙亮，0.93）、#481（第二轮：远站 0.239，近处 0.067）。目标图 `cam01` 上这个比是 0.04。

**6. 基准季时的整体明度和彩度，照这一关的参考图定带子。**
- 数（T00 的 J01 夏昼，六个验收机位）：L50 在 26–36，L95 在 60–72，平均彩度不低于 7.5。
- 量：`python3 tools/look.py <图>`，T4 的图。参考图 `refs/t00-atlas/T00.lossless.webp` 量出来是 L05 11.6、L50 31.8、L95 67.6、彩度 10.0；带子是参考图的 L50 ±5、L95 −8/+4、彩度的四分之三。
- 参考图是生成图，只定明度和气氛，不定构图和构造。数用工具量，不手算：我手算的彩度比 `look.py` 低两成。
- 出处：#470，`docs/ART-REVIEW.md` B1（六个机位 2026-11-17 的读数：L50 12–35，彩度 3.3–7.6）。

**7. 灯是少的。**
- 数：黄昏时亮着的窗不超过画面里窗总面积的三分之一；相邻两扇亮窗的亮度相差 15% 以上。
- 例外：原型或目标图点了名的那一处灯，可以整座亮。T00 是 `art5` 的观音殿（原型 05「窗格透出暖光」），五间全亮是对的：三分之一的上限防的是满院的灯，观音殿就是「一盏灯」里的那一盏。整座亮的时候，各扇仍要有深有浅、下亮上暗，同一画面里别的殿不跟着亮。
- 量的时候先看这个机位在不在例外里；`art3`、`art4`（首院）照三分之一。
- 出处：`docs/ART-REVIEW.md` A2（`art3`、`art4` 秋暮，每扇窗一样亮的橙色面板），#459；例外出自 #509（审图二判 `art5` 观音殿全亮是「留」，T00 主创转达）。

### 形与构图

**8. 白盒只判体量、比例、构图和明暗关系，不判材质。但这四样要判实。**
- 构件要读得出来：九间的殿，远站的图上数得出十根檐柱。出处：#425 第一轮，檐柱只凸出墙面 2 厘米。
- 剪影上不能有穿出来的东西：屋脊下伸出的槫头。出处：#425 第一轮；单测只查了梁，没查槫。
- 挪机位会把原来画外的毛病带进主画面：屋脊兽与近物（树冠、柱）之间留不少于画宽 4% 的天，或者明确盖住，不要相切（`ART-SPEC.md`）。出处：#474，`art3` 挪到枫树下，树坑的硬边黑片进了左下角，鸱吻离树冠边只剩 10–40 像素（1280 宽）。
- 站点要站在该站的地方：机位的「必看」逐样核对，看到几样写几样。出处：#425，B 站在月台上面，台基在脚下看不见；改到踏道脚下 1 米，又被踏步占满，四样必看只见一样半。**站点的数要拍了再定，我给过的数也要改。**
- 主角放进去再判空间：殿的梁高，要放了像的体块才看得出够不够。出处：#425 第一轮，最低一层梁在 7.2 米，像连坛顶高 9.5–9.9 米。

**9. 和目标图比比例，量分段占总高的比例，不比绝对尺寸。**
- 做法：正面图上量各段的像素，除以总高；目标图同样量。差在哪一段，就改哪一段的数。
- 出处：#438，地面到小额枋下皮占总高 52%，目标图 61%；改到 60% 通过。
- 目标图是生成图，只定比例和气质，不证明构造和年代。它和规范里的机位数冲突时（`cam01` 站在 55 米处殿只占画宽六成，目标图撑满），写明两个选项和推荐，交主创定。

**10. 「从 A 处看得见 B」写成画面上的条件，不写成某一座的绝对高度。**
- 数（T05 的 `cam07`，第一人称，1280×720）：B 的正脊全长露出（上限以「前面没有框子时」为准）；中轴那一列像素上，从挡在中间那座的最高点到 B 的正脊下沿，露出的瓦面 ≥ 画高的 1.5%（≥ 11 像素）；B 的脊饰顶到前面框子的下皮留天 ≥ 画高的 1%。
- 做法：先拿眼高、几座的脊高和距离算一遍仰角，知道哪个方向的改动有用（中间那座往眼这边挪会挡得更多，眼往后退才让得开），再用射线逐点量、出图来核。估的数要说是估的。
- 做框的那一座（牌坊）自己的屋脊线上面只留天：它前后一段距离内、中轴两侧不立树（T05：牌坊南北各 17 米以内、离中轴不到 8 米）。#492 `6095ba4`，两棵树的冠从牌坊屋顶后面顶出来，回望时像两只耳朵。
- 出处：#464、#492。我第一次给的是「无量殿脊在院地面上 +8.5 米以内」，它只在一个位置成立，还要举折 0.173，低于《营造法式》的下限 0.25；改成画面条件（#464 评论 7060347115）。第二条先估的是 2%，图出来以后 1.5% 已经读得出「后面还有一座顶」，守 2% 要再退 7 到 10 米、牌坊更小，改成 1.5%（#492 评论 7061732268）。射线量出来挡住正脊的是牌坊的雀替，不是我估算时盯着的无量殿。**判法不能逼着有出处的构造去迁就；没有图时估的线，有图以后要回头改。**

**11. 一排一样的东西要打散，一片满铺的东西要分开。**
- 出处：#457（甬道墙到墙满铺石板像马路，改成 6 米甬路加两边土面）；#464（树干占位是两排成对的电线杆）；`ART-SPEC.md`「磨损有原因」。
- 反过来，该统一的要统一：七尊的光背一样大（#407），不为避让一处把其中两个做小。要避让就七尊一起改（#493：统一 4.0 米，光背与梁面每边留 ≥ 0.15 米）。

**12. 树冠要透，背光的叶不能是褐的。**
- 数：同机位秋昼，冠上亮金与暗褐金的面积比 ≥ 1.5:1；夏昼树冠的平均亮度 ≥ 同画面柳杉冠的 1.3 倍。
- 量：按色相挑出叶子的像素，新旧同一画框。
- 出处：#327，新冠成了实心锥，亮金面积少四成、暗褐多近两倍。**新做的比旧的更合资料，不等于更好看，要新旧并排看。**

**16. 大面要有块面的深浅，细缝在远处会消失。**
- 数（T00 `cam06` 夏昼的中景，1080p 第 705–850 行、第 300–1620 列）：切成 16×16 的小块，各块亮度标准差的中位数不低于 14。
- 做法：改前改后并排裁同一块图看，近、中、远各裁一块。石头靠自己的深浅读，不靠缝。
- 出处：#474 `b0557fa`（审图二，[评论](https://github.com/bolechen/temple-walk/pull/474#issuecomment-7061326843)）。缝从 3–8 厘米收到 0.9 厘米是对的，但同一次把石板之间的明暗差从 2 倍收到 1.6 倍，中景的这个数从 18.5 掉到 10.1，读成湿水泥；近景只从 6.8 到 6.4，所以只看近景会漏。#486（石阶）同理：隔二十米仍看得出深一块浅一块；近看缝的深浅随位置变，等宽纯黑的缝加刀切的棱读成预制块。

**17. 眼睛新到的地方，转一圈看背面。**
- 数：画面里没有比周围亮两倍以上的平面；没有通到外面的缝；殿内同一高度上，任何一面墙的亮度与别的墙相差不超过一倍。
- 做法：凡是让眼睛进到以前进不到的空间（退进门里、走进殿内、绕到像后），在那里转一圈拍，仰看一张。
- 出处：#411（眼退进门后，±40° 时看到空壳殿的内侧：槛墙内面屏上亮度 120，旁边门扇背面 24、地面 27）；#481（T05 殿内的白墙和院墙合在一起按室外画，山墙内面的亮度 0.13–0.29，是后墙 0.025 的八到十倍）。

**24. 远景的山不压主体：换形不能丢笔触。**
- 数（T00 开场第一格）：画面中间一半宽度内，高过主体（凌霄阁）檐口的山，与天的亮度差不超过 6%；任何一座山比天暗不超过 10%；山脊线不从主体的檐口和屋脊之间横穿。
- 出处：#465 `49c061d`（#183 的地形试验，审图二，[评论](https://github.com/bolechen/temple-walk/pull/465#issuecomment-7061464681)）。真实高程的山形是对的，但轮廓成了光滑的线、山脚没有雾，开场第一格被一道深色山脊压住：现在的山环是 0–5%，两种候选是 20–21%，阁自己约 30%。是判法 1 的远景版。

### 人在画面里、镜头、验收里的数怎么写

**13. 「他在画面里」要看画面，要转着看，要在页面上看。**
- 做法：
  1. 用 `__pick(x, y)` 打他身上几个点，看最先碰到的是不是他；或者从眼到他的腰和头各打一条线，不被挡（`eyespace.sees`）。`monkBox` 只说明他投影在画面范围里，不透明度是 1 也不说明没被挡住。
  2. 用真实按键转视角：至少 ±40° 和 ±65°；新的眼睛落点从 −90° 到 +90° 每 10° 一档，来回各扫一遍，停稳再判（落点和从哪边转过来有关，藏经楼、凌霄阁只有一边黑）。
  3. 画面的平均亮度不低于正面那张的一半。全黑就是眼进了殿的空壳。
  4. 在预览页面上用 `__frame()` 读眼的位置和距离并拍图。单测过只算辅证：Node 里眼停在 1 米，页面里是 4.3 米。
  5. 为了看见他而压低的俯角要有上限：平视时画面被压到俯 41°，整张图是地面和墙脚。上限的数（审图二提的是额外俯角 25°，超过就缩臂）还没定。
- 出处：#411 第一轮 `c08c42c`（审图二，[评论](https://github.com/bolechen/temple-walk/pull/411#issuecomment-7060098314)；`LESSONS.md` 同名一条）、#396。作者交的四张都正对门外，都好；毛病在转过去以后。

**14. 像素、方差这类数是代理指标：先确认量的地方真有东西，数和图冲突时看图。**
- 做法：把一个数写进验收之前，在那个机位上看一眼要量的那片区域里有没有要量的东西，写清在哪几行、哪个距离量。量出来的数和图冲突时，以图为准，把验收改成看图判，数留作证据。不为凑数去改设计。
- 例：首院铺地的「缝在屏上 ≤ 2 像素」，原意是近处的缝不读成粗黑格子。`__pick` 逐行量下来，`cam06` 均值 1.34、最大 1.86 像素，`art3`（眼高 0.81 米）均值 2.36、最大 3.59；两个机位的画面中间三分之一几乎没有铺地，在那里量等于没量。把缝改细能让 `art3` 过线，但 `cam06` 中景的缝会消失。最后定的是：缝保持 0.9 厘米，过不过看图判（近处不读成粗格子，中景不消失）；中景太淡就加深缝色或加苔，不加宽。
- 「下三分之一亮度方差要升」这类方差也一样。#474 改好以后方差反而降了（13.4 到 10.2）：旧的方差全来自粗黑的缝。整片在阴影里时方差也小，不等于前景是空的。
- 出处：#474、#467 评论 7060324596（T00 主创的裁定），数据随 #474 合入（`docs/t00/evidence/ground-467/joint-rows.json`）。

**15. 两头有张力的要求写成带子，不只写下限。**
- 数（T05 `cam03` 第三人称，1080 线）：中尊头顶比相邻两尊高 25–38 像素（画高的 2.3%–3.5%）。低于下限读不出「略高」，高于上限读成一主二从。
- 出处：#493。只有下限时，实施的一方会一直往上加。

### 人物

**25. 人物的颜色用比例判，在场景的光里判，在两个距离上看。**
- 数（小沙弥）：袍的亮度 ÷ 额头的亮度 = 0.25，允许 0.22–0.28，和设定图上的同一个比值对。
- 机位：首院，正面 1.9 米，眼高 0.85 米，夏昼；新旧身体同站位同机位各一张，取袍、额头、裤各 12–16 像素见方的中位数。
- 两个距离：跟随镜头（1440×900 上他约 208 像素高，是玩家平时看到的）和 1.9 米近景各一组；再加每个仪式自己的机位（`?show=shot-<id>`），那是玩家看到脸的地方。毛病写明在哪个距离看得见：只在近景和拍照模式看得见的记「应该改」。
- 出处：#469 第一轮，预览 `ceb06d0`（审图三，评论 7061966120）。作者交的是灰底舞台上的图，袍看着比设定图还浅；进了场景袍是 L\* 16，彩度只有设定图的一半，比身后的木门还暗。静坐机位上他睁眼往旁边看，只在那个机位上才发现。和判法 3 是一回事：舞台的光和场景的光不是一回事。

### 界面与文字

界面的判法出自审图三（T00 界面与人物）和审图二，2026-11-21。界面是各关共用的，T05 照搬。

**18. 多件 PR 改同一处界面，合起来看。**
- 命令：审界面 PR 之前，对每个在途 PR 跑 `git diff main...<分支> -- app/index.html app/src/ui.css`，列出各自往哪个容器里加了东西。同一个容器被两件以上动到，把宽度加起来，在 360 像素宽、四种语言上算。
- 出处：#476 `55256f3`、#483 `53bbdf0`、#455 `5ca14f6`，统一的做法在 #473 评论 7061334967。三件各往朱印帐底排加一个按钮，各自的 `mobile-audit` 都过；合起来七个共 641 像素，390 像素宽的手机只有 358。

**19. 纸上的东西只有这几样：字、一枚印、`paper.js` 画的圈和线。**
- 命令：在新增的 CSS 和 HTML 里搜 `<circle`、带 `border` 的 `border-radius: 50%`、不带 `mask` 的 `conic-gradient`，有就不过；圈、线、印用 `--enso-light`、`--enso-red`、`--brush-ink`、`--stamp`。
- 数：一张新的纸里，除了印，带 `border` 或底色的元素是 0 个（链接、输入写成一行淡字，照 `#blessLink`）；`#<纸> .stamp` 只有一个，盖在这张纸要做的那件事上，不盖在「合上」上。
- 同一个手势只有一种样子：新出现的 `role="progressbar"`、圈、长按，先搜别的在途 PR 有没有同一个手势，两张图并排，除了位置和字看不出是两个东西。
- 出处：#483、#455（「按住等一圈画满」一件是 44 像素的细线圆在右下角，一件是 104 像素的圆环在画面中间；光滑的几何圆读成网页的加载圈）；#476（392×72 像素带边白底的输入框；印盖在「合上」上）。

**20. 纸打开的第一张图上没有焦点框；不按不出现。**
- 做法：开纸立刻截图。`document.activeElement` 是纸本身，不是第一个按钮；按一次 Tab 才出现描边。出了框，多半是没走 `ui.open()` 而直接 `showModal()`。
- 静止时截图，画面上只有字。指示进度的东西只在进度大于 0 时可见；不需要进度的模式里永远不可见。
- 出处：#476（「不用了」外面套着橙色方框）；#483（收尾那一分钟里一个空圈从头挂到片尾）。

**21. 画面中间那一条留给小沙弥。**
- 命令：`__probe().monkBox` 向外扩 8 像素，与界面元素的框不相交。
- 数：跟随镜头下他占画面高度的 46%–70%，中轴左右各半个身位，六种屏幕都是。
- 出处：#461（做法在评论 7060469180）、#455。标题页的印盖在他头上、「入山」压在腿上；长按的圈悬在他头顶，读成背光。

**22. `mobile-audit` 查不出的三样，自己量。**
- 数：相邻两个元素的间距不小于 16 像素；折行后没有少于四个字的行，或短行不少于长行的六成；一排里每个 `.stamp` 的 `top` 等于同排第一个的 `top`。
- 机位：六种屏幕（桌面 1440×900、1024×640；竖屏 390×844、360×640；横屏 844×390、667×375），中日英韩四种语言，新访客和回访（有印、有上回的地点）各一遍。最紧的总在 360×640 和 667×375。
- 出处：#447（横屏 844×390 上两行字离「入山」只有 3 像素，改前 27；回访多出「从头走起」和已得几印那一行，离底下的地名只剩 4 像素）、#476。没出屏、够 44 像素、够 12 像素，审计全绿。

**23. 界面的词用这座寺自己的话，在每个季时、每种语言里都是真话。**
- 命令：新词先 `git grep` 它在 main 的 `app/index.html` 和 `app/locales/` 里出现过几次，0 次的要问；新字先查在不在 `app/shared/fonts/chars.txt`。
- 做法：
  - 数字在中文、日文里写汉字（「已得二印」，不是「有 2 枚印」）。
  - 写在画面上的话，`?season=` 四季各拍一张对图：标题页写「雨后」「路还湿着」，冬天的底图是雪。
  - 地名、专名每种语言单看一遍会不会撞上当地的同名词：「江南」的韩文只写「강남」会读成首尔江南区。
  - 成对的纸（带走和带入）标题各读一遍，站在看的人那一边说得通。
  - 后果最重的一句不能是最淡的一句；有条件才成立的话，条件不成立时不显示。
- 出处：#476（「存档」在 main 的界面里一次也没有；点开链接的人看到的标题是「带走存档」；「会覆盖现在的进度」是全纸最淡的 14 像素）、#483、#447 `81fc038`（审图二，[评论](https://github.com/bolechen/temple-walk/pull/447#issuecomment-7059047839)）。

## 四、「好的要保住」

`docs/ART-REVIEW.md` 每一关有一张「现在好的」清单。审任何 PR 时，把清单里和这次改动同一处的画面重拍一张，和改前并排；变坏了就是不通过，哪怕 PR 自己的目标达到了。动全局的光、雾、调色时，清单上的每一张都要重拍。清单里的东西被改得更好了，就改清单。

## 五、结论怎么写

- 第一行：「美术通过」或「美术暂不通过」，加看的提交号。
- 「怎么看的」一段：看了哪些图，哪些是自己拍的，哪种渲染，哪些没看到。
- 每条意见写四样：哪里（机位）、看到什么、改成什么样（尽量给数）、依据（规范的哪一条或哪张目标图）、怎么判。
- 分三类：必须改；应该改；通过的。通过的也要写，作者要知道哪些别动。
- **通过要写范围。** 不动 `app/` 的 PR、白盒的 PR，可以通过「这一步」，把访客真正看到之前必须过的条目列出来，写明带到哪一项去判（#407 第七轮通过的是分区法和配方，进殿前六条另列进了 #463）。没有去处的条目会丢。
- 中间稿只判方向：「是这条路」或「不是」，加下一步。
- **自己算错了、给的数拍出来不对，在评论里直说并改。**（#438 的「板 0.6–0.7 米」没算枋自己的厚度；#425 的 B 站。）
- 每条评论末尾带 Claude Code 的署名行。

## 六、几边意见不一致时

- 形体对不对归 3D 评审，构件合不合营造归结构评审，好不好看、合不合方向归美术。各写各的结论，并行。
- 好看和有出处的形制冲突时，不为了好看改掉有出处的东西；写清选项和推荐，交主创转所有者。
- 几位美术审图之间口径不一致，以美术总监为准；美术总监和所有者的话不一致，以所有者为准，但要先把理由说清（`AGENTS.md`「最高价值观与铁律」）。
- 排期归主创。美术可以说「这一件要先于那一件，否则判不了」（#432 放体块之前要先有 #481 的曝光）。

## 七、美术不做的

不写游戏代码，不合并，不关 issue，不花 Tripo 点数。要出概念图，写提示词交主创转所有者。不是自己那一关的活，原样转给管那一关的审图，不顺手看。
