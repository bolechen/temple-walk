写给接任的建筑结构评审会话。只读这份、`AGENTS.md`、`CLAUDE.md` 就能开工；别的按链接查。对所有者和主创一律用中文。

## 一、职责和评审时的标准

**职责**（`AGENTS.md`「常驻的专项评审会话」）：管营造规制、构件、台基踏步、殿内陈设的依据。主创在写验收标准前、合并看得见的形体改动前来问。意见写在对应 PR / issue 的评论里，再 `send_message` 给主创；最后取舍是主创的，我不同意时写明理由。独立评审（`docs/t00/independent-review.json`）是另一回事，结论谁也不能代改。不弹出、不批准任何「信任 / 使用我的电脑」卡片，否则子会话消息收不到。

**评审的做法**
- 用《营造法式》给出**可量的**数：材等、份数、开间、举折、出跳。每条评审一个编号（`structure-review.md` 的 S-01…S-17），写「现状 → 规制 → 建议数 → 怎么验」。
- 建议的数先拿代码核一遍再给。我犯过两次错：S-03 建议禅堂/茶寮取 0.205，应是第四等 0.223（在 #133 上认了）；回廊的宽度先看 `COL_R`、`BODY`、栏杆内缩再给数。
- 来源一律标三档：**原文**（读过原文）、**转引**（别人引的）、**记忆未核**（我凭记忆）。项目规矩：不得把推断当出处（`docs/t00/SOURCES.md`）。没有定数的写「按常理」或「自拟」。
- 这次会话里读不到《法式》原文（搜索引擎查不到卷三踏道、台基）。凡引卷三的都是记忆未核。要写进 `SOURCES.md` 的数，请继任者先去 [Wikisource](https://zh.wikisource.org/) 或 CBETA 读原文，读到再改标签。
- 记忆里常用的规制（全部未核，除非 `SOURCES.md` 已转引）：
  - 材分八等，一份 = 材广 / 15；一宋尺约 0.31 米。
  - 铺作各件份数：栌斗 32、泥道栱 62、华栱 72、慢栱 92、令栱 72。
  - 补间：心间用两朵，间广不匀时相邻补间之间相差不过一尺。
  - 举折：殿阁取三分举一，㼧瓦厅堂取 0.27。
  - 副阶 / 缠腰：材分减殿身一等。
  - 平坐：铺作比上屋减一跳或两跳，普拍方厚随材广，雁翅版广加材一倍。
  - 椽每架平不过六尺。
- 不要照美术原型改建筑（`docs/t00/art-goal.md`）：原型里 AI 编出来的构件不是目标，建筑以结构评审为准，原型只管光和色。

## 四、工具和看图方法

- 预览：每个 PR 一个地址 `https://pr-<编号>-temple-walk-preview.bole-chen.workers.dev`；固定到某次提交用 `https://<部署号>-temple-walk-preview.…`（`docs/PREVIEWS.md`）。地址后面加参数：`?cam=x,z,yaw,pitch` 站到任意位置，`?show=<view>` 用已命名机位，`?in=<hall id>` 进殿，`?up=lingxiao` 站上平坐，`?shot=1` 冻结时间、藏控件，`?season=…&time=…` 换季节和时辰。
- 本地出图：`node tools/shots.js <view>[@season-hour][@first|third]`（`tools/out/*.png`）；殿内用 `node tools/inside.cjs tools/out '[{"hall":"main","name":"x","abs":[x,y,z,yaw]}]'` 或 `--views t00`。屋角三向、台基侧面等**自选角度**，我写过一个小脚本：起一个 `tools/site.cjs` 的静态站点，用 Playwright 打开 `?cam=…`，并可在页面里调 `__pick(x, y)`。脚本在我的临时目录里，不在仓库里，继任者需要的话照 `tools/shots.js` 的写法重写；宽幅 1280×536 看起来更接近原型的 2.39:1。
- 页面里的钩子：`__pick(x, y)` 问某点是什么（部件、材质、距离）；`__probe()`、`__views`、`__halls`、`__lofts`。
- 测试：`pnpm test`（`tests/unit/` 里有 `plan`、`stairs`、`eaves`、`sweeps`、`loft`、`framing`、`interior`）；`pnpm run edges`（身体有没有进建筑）；`pnpm run nearplane`；`node tools/cameras.mjs`。
- 色调：`python3 tools/look.py --check <art1…art6> <图>`；目标在 `docs/t00/art-targets.json`。
- 复核结构 PR 的清单：三向对照图（正、侧、斜俯视，改前改后并排，见 AGENTS.md 新规）；`art1`–`art6` 重拍；`nearplane` 全过；几何不超过 1 毫秒的预算（`structure-goal.md`）。
- GitHub：只用 GitHub MCP 工具，没有 `gh`（搜索例外）。强推被禁，用合并代替；评论末尾带「Generated by Claude Code」页脚。

## 五、踩过的坑

- 评审里给的数要先核代码。S-03 的 0.205 错过一次。
- 「合并后的 PR 没带最后一次提交」：#70 合并时漏了 80dfe03，后来是用 cherry-pick 补进 #73。合并前核对 head。
- 本地 `notices.test.mjs` 因缺 `vendor/basis/LICENSE` 失败，main 上同样，是环境问题，不是改动造成的。
- 渲染要等：`tools/shots.js` 在 SwiftShader 上每帧可能一秒，别用秒数等，用帧数。同时跑多个 Playwright 渲染时，别杀错进程。
- GLSL 片段末尾不能有 `//` 注释；内联注释会把后面的代码注掉。
- 文档合并冲突（`delivery.json`、issue 模板）：取 main 的版本，再把自己的条目加到前面。
- `walk.roofs` 记的是檐下范围，雪和眼睛都读它；建筑改了檐，别忘了 `shelter.js` 的格子。
- 同一个答案别在多个 issue 里各写一遍：写在一处，其他地方链接。
- 来源标签别升级。读到原文之前，「记忆未核」就是「记忆未核」。
