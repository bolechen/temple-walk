# 目标：按结构评审修改木构（给实施方）

写于 2026-11-16。依据是 `docs/t00/structure-review.md`（下称「评审」），评审对象是 `452f14e`。
到 `7134ec0`，`building.js`、`site.js`、`framing.js`、`interior.js`、`geo.js` 都没有再改过，所以评审对现在的 main 仍然成立。
实施方开工前先读评审全文、`CLAUDE.md`、`docs/HANDOFF.md`，以及 `docs/JINGSHAN.md` 的「有意没有做的」一节。

## 要达到什么

全寺的木构在一眼看得见的地方合乎《营造法式》，让 `docs/ART-SPEC.md` 里「斗拱、梁架、屋面与柱网通过结构检查」这一条，在下一轮结构复核时可以勾上。
画面精美庄严仍是第一原则：法式和画面冲突时，停下来写明冲突，交给所有者决定，不要自己取舍。

## 范围和顺序

按下面的顺序做，每一阶段单独一个 PR。每个 PR 都要能独立合并、独立回退。

### 第一阶段：开间和补间（评审 S-04、S-05）

- 改 `building.js` 的 `between()`：心间放两朵补间铺作，其余各间一朵，不再看开间是否大于 4.6 米。
- 按评审 S-05 重排五座建筑的开间（大雄宝殿、释迦宝殿、藏经楼下层、观音殿、山门上层）。要求：
  - 心间最宽，向两端渐窄或相等；
  - 相邻两朵补间的距离，彼此相差不超过 0.31 米（法式「每補間鋪作一朵不得過一尺」）。
- 大雄宝殿上檐的柱线要跟着下层的内圈柱线走：开间按评审给的数改，上檐 x 落在 ±10.8 米。
- 先写会失败的单元测试，放进 `tests/unit/`，然后再改：
  - 「每座建筑心间两朵补间，其余一朵」；
  - 「开间自心间向外不增」；
  - 「补间朵距相差 ≤ 0.31 米」。

### 第二阶段：举高（评审 S-06）

- 在 `site.js` 里加一个函数，由前后橑檐方心的距离算出 `rise`：
  - 殿阁、楼阁取 1/3；
  - 厅堂（禅堂、茶寮、药师殿、大慧院）取 0.27；
  - 腰檐、副阶取 1/2；
  - 攒尖亭照现状。
- 每座建筑不再手填 `rise`。
- `profile` 改成按架数逐缝折下的折线（卷五 举折之制），橑檐方以外接一段顺着最下一架坡度的直檐。翼角的起翘 `lift` 保留。
- 测试：「每座顶层屋面的举高比在法式值 ±10% 以内」。
- 注意：这一阶段会改动 `walk.roofs` 的高度、`shelter.js` 的遮雪图、`eyeShut` 和眼睛的避让。`eaves.test.mjs`、`sweeps.test.mjs`、`shelter.test.mjs` 必须全过，必要时随之更新。

### 第三阶段：楼阁的柱位和平坐（评审 S-01、S-02）

- `putStack` 的上层柱线必须落在下层某一圈柱线的正上方。涉及山门、藏经楼、凌霄阁、御碑亭、大雄宝殿进深方向。
  - 山门下层只有前后两排柱，可以在中间加一排内柱，或者把上层进深做成与下层相同。选哪一种，写进 `docs/t00/decisions.md`。
- 每个上层下面加平坐（卷四 平坐）：
  - 普拍方上坐铺作，铺作比上层减一跳；
  - 外加雁翅版，栏杆立在雁翅版内；
  - 腰檐收在平坐下面。
- 测试：「上层每根柱子的正下方都有下层的柱子或平坐柱」。
- 山门是验收机位 CAM-04、CAM-05 的主体，改完逐张看这两个机位。没有新的运行证据，不得改 `acceptance-report.json` 的结论。

### 第四阶段：角梁和材等（评审 S-07、S-03）

- 每个屋角加大角梁和子角梁：从转角铺作上斜出到檐角，梁头卷杀，子角梁头略翘。
  - 风铎改挂在子角梁头下；
  - 翼角椽改为沿角梁排开。
- `buildHall` 加一个 `cai` 参数（材广，单位米）。斗拱、阑额、柱径、椽径都按「分」乘它。站点表按评审 S-03 的建议取值：大殿 0.256，观音殿、山门 0.232，配殿 0.205，钟鼓楼和亭 0.186。
- 测试：
  - 「斗拱各件按材分换算后，与卷四的分值相差 ≤ 5%」；
  - 「每个屋角都有角梁」。

### 第五阶段（可选，所有者点头再做）：次要项

评审的 S-08 到 S-13、S-15、S-17，依次是：飞子，侧脚、生起和檐口生出，椽距、椽径和布椽，柱高大于间广，方石柱础，托脚和襻间，殿阁室内柱头铺作，凌霄阁鸱尾。
S-14（殿内房间比外观大）和 S-16（屋顶等级）涉及设计取舍，先问所有者，不要自己改。

## 每个 PR 都要做到

- **测试先失败，后通过。** PR 描述里写明测试在改动前失败的输出。
- **检查全过。** `pnpm run check`、`pnpm run typecheck`、`pnpm test`、`pnpm run edges` 全过。动了 `app/` 的，推送前跑 `pnpm run verify`。
- **截图。** 用 `node tools/shots.js` 拍改动涉及的机位（至少 `gate`、`fiveroofs`、`hall`、`library`、`guanyin`、`summit`，以及 `cam01`–`cam06`），逐张看过。前后对照图放进 `docs/t00/evidence/structure/`。
- **测性能。** 角梁、平坐、飞子都会增加几何。改前改后各跑一次 `tools/gpu-render.sh`（或至少用 `__census()` 记三角面数和绘制次数），数字写进 `docs/HANDOFF.md`。首院高档单帧不得比现在（约 9.3 ms）慢 10% 以上；超了先停下来报告。
- **登记来源。** 每改一处看得见的东西，同一个提交里在 `docs/t00/SOURCES.md` 写一行：引卷次和原文；是推断的写「推断」，按常理的写「按常理」。
- **更新评审记录。** `docs/t00/review-log.json` 里对应的 STR3-xx 改为 `fixed_pending_retest`，`fixed_in` 填提交号。结论留给复核人改，自己不要标 `verified_closed`。
- **写 HANDOFF。** `docs/HANDOFF.md` 加一行：做了什么，还差什么。
- **代码与提交格式。** 代码注释用英文，写成描述地方的散文；文档用中文。提交信息和 PR 标题用 Conventional Commits。

## 做完的标准

- 第一到第四阶段全部合并，CI 全绿，`pnpm run edges` 为零超限。
- STR3-01 到 STR3-07 都标为 `fixed_pending_retest`，并且附有截图和测试。
- 由结构评审方（不是实施方）对照评审逐条复核；复核通过后，才勾 ART-SPEC 那一条。

## 不要做的

- 不要为了合法式去动 `JINGSHAN.md` 里有出处的格局，比如五凤山门的五个屋顶、东钟西鼓。真冲突时写出来，交给所有者。
- 不要关掉或跳过任何测试来求绿。
- 不要一次 PR 把几个阶段混在一起。
