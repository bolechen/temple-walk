# 树改用现成生成器：试验报告（#162）

第二轮的做法、图和结论见下面「第二轮」一节；第一轮的内容保留在后面。

日期：2026-11-18。分支：`claude/trees-162-spike`（基于 main `5cb8bb2`）。这是试验，没有替换 main 上的树：只有加了 `?trees=three` 或 `?trees=ez` 时，首院西侧那棵枫（-9.5, 28）和院中柳杉（-19, 29）才换成现成生成器长的，其余树和不带参数的页面都和 main 一样。

## 结论（建议，由所有者看图定）

**建议换成 three.js 自带的 `TreeGenerator`（vendored 一份），打两个小补丁（枝梢封口、枝领），叶子、树皮、季节、积雪仍用我们自己的。不建议用 ez-tree。** 理由：

- **根脚接缝从结构上消失。** 树干的根部外扩（root flare）就是树干本身的一段，没有单独的根脚，所以 #91 剩下的那条细暗线不会再有（`cedar-hand-three-ez.jpg` 第二行：手写版膝高处有明暗断口，three 一体）。
- **它就在我们已经装的 three r186 里，没有新依赖。** 代码 gzip 后约 4.8 KB；平行移动标架（不扭）、管道模型、非线性收分、种子固定，这些是 #92 要求的，它已经有了。
- **代价可控。** 首院 T4 帧耗 +0.36 ms（12.93 → 13.29，三次交替的均值，噪声约 ±0.4），绘制次数不变，三角面略增。
- **要补的。** 枝梢是开口的管子（#92 的「开口」问题还在）；子枝从母枝轴线起步，没有枝领；只长一根主干，多干的枫要几棵斜放拼起来（本试验就是这么做的）；不长叶子。这四处都是在 vendored 那份里加几行就能做的。

**不建议 ez-tree：** 按我这次调的参数，枫的大枝是长弧、末级枝细成一根根线（`maple-hand-three-ez.jpg` 第三列），根部没有外扩，标架用欧拉角累加；自带的树皮、树叶贴图来源不清（两张来自 texturecan.com，树叶图没写来源），不能随项目发布；代码 gzip 后约 9 KB。它的长处是常绿树模式（柳杉的层叠枝）和自带叶片位置，但都不足以抵消上面几条。

**手写版本身也是一个选项。** #92/#93 的手写版（`claude/trees-92-93-forks`，518ce43，未开 PR）已经有枝领、封口、管道模型和多干鸡爪槭，这几处正是 three 版要补的。所以真正的选择是：「three 的骨架 + 我们补枝领封口」，或者「继续手写」。我倾向前者：骨架那部分交给 three.js 维护，我们只维护叶子和补丁，以后别的关卡复用也更省事。最终由所有者看图定。

## 第二轮（2026-11-18，按主创和 3D 评审在 #186 的意见）

### 做了什么

**枫改成混合法。** 前两级由我们按评审表画（`app/src/spike/gens.js`）：

- 一根短粗主干带根部外扩，在 1.0–1.4 米处分成 3–5 根骨架枝。
- 每根骨架枝 5 个控制点，半径为主干的 0.46–0.58，截面积之和为主干的 1.00–1.06，与竖直夹角 50–61 度，越往外越平，分两三层。
- 三级以下交给 three 的 `TreeGenerator` 从每根骨架枝的末端接着长，并在骨架枝中段长出侧枝。
- 主干只长到最高一根骨架枝之上 6 厘米，不在分叉上留桩。
- 树下补上树坑（`bed()`）。

**vendored 的 `three-tree.js` 补了几处：**

- 枝梢收成一点，不再是开口的管子。
- 每根子枝在离开母枝处鼓出枝领，约 0.3 米内回到自身粗细。
- 子枝半径按母枝基部半径的份额算（三分时 0.577，两分时 0.707），子枝细过最小半径就不再分叉。所以生成器长的每一个分叉，子枝截面积之和都是母枝的 1.00 倍。
- 记录每个分叉的半径，供测试读。

**柳杉叶子改挂法。** 不再用一团团叶片卡，改成和手写柳杉一样，每根枝顺着挂一片下垂的叶片。冠部不再发黑（`round2-wide-*.jpg`），冬天也能积雪。

**单测。** `tests/unit/tree-spike.test.mjs` 5 项，读骨架量评审表的每个数，用五个种子（7、3、9、21、40），树高都按院中那棵枫取 7.5 米：

| 项 | 评审表 | 实测（五个种子） |
|---|---|---|
| 树高 | 3–7.5 米 | 6.7–7.3 米 |
| 冠幅 / 树高 | 1.0–1.3 | 1.11–1.26 |
| 分枝高 | 0.8–1.5 米 | 1.07–1.37 米 |
| 主干 0.3 米处直径 | 0.2–0.3 米 | 0.26 米 |
| 骨架枝 / 主干半径 | 0.45–0.6 | 0.46–0.58 |
| 骨架枝截面积之和 / 主干 | 0.8–1.2 | 1.00–1.06 |
| 骨架枝与竖直夹角 | 40–65 度 | 50–61 度 |
| 冠的层数 | 2–3 | 2–3 |
| 生成器长的每个分叉 | 0.8–1.2 | 全部 1.00 |
| 木头三角面 | ≤ 8,000 | 5,875–6,709 |

用第一轮的枫跑这组测试，5 项里 4 项失败，只有冠幅比那一项过。层数是按骨架枝的起点分组数的，不是从画面上量的。

### ez-tree 自带预设

`?trees=ezp` 用 ez-tree 自己的 ash_medium（阔叶）和 pine_medium（针叶），按原值长出来再缩放到树高（`round2-ez-presets.jpg` 第三列）。

- 阔叶那棵是一棵像样的温带树，第一轮那张「长弧、细线」的样子主要是我调的参数不对，不是算法的问题。
- 但它仍然没有根部外扩，标架是欧拉角累加。预设里也没有鸡爪槭或柳杉，要像就还得调参，等于回到第一轮的位置。
- 预设的数值对我们的骨架没有直接参考价值：它的单位是自己的，层级结构也不同，所以没有借用。

### ez-tree 贴图的许可

- 仓库根目录的 `LICENSE` 是 MIT，只说软件，不提贴图。
- README 没有贴图的来源或许可说明。
- npm 包里 `src/lib/assets/bark/README.md` 写了树皮的来源：两张来自 texturecan.com（221、588），两张来自 Poly Haven（bark_brown_02、bark_willow_02）。
- 树叶四张没有任何来源说明。
- texturecan.com 和 polyhaven.com 从本会话的网络连不上，所以这四张树皮的许可原文没有核到。
- 结论：ez-tree 自带贴图的许可一张也没有核实。我们本来就不用它的贴图，这一条不影响方案。

### 第二轮的结论

- **柳杉：** 建议用 three。根部和树干一体，接缝消失；冠形和手写版相当。
- **枫：** 混合法（我们画前两级、three 长三级以下）能达到评审表的每个数。画面上冠宽、冬态枝细密。我认为可以换，但三级以下偏直，这一点要所有者看图定。如果所有者觉得不像，退路是「柳杉用 three、枫留手写」。

## 怎么试的

- **两个生成器都 vendored 在 `app/src/spike/` 下，各自带 MIT 许可原文。**
  - three 的 `TreeGenerator` 去掉了 WebGPU/TSL 材质：它一 import 就会把整个 `three/webgpu` 拉进来，我们是 WebGL 渲染器。
  - ez-tree 去掉了预设（JSON）和自带贴图，索引改成 32 位（大树会溢出 16 位）。
- **生成器只给木头几何和叶子挂在哪里**（`app/src/spike/gens.js`）。木头用我们的 `M.bark`，叶子用我们的叶片卡（`clump`），所以季节换色、秋红、冬天落叶后露出细枝卡、积雪、风摆都和现在一样。
- **枫：** 两个生成器都各长三棵、斜着从一个根脚伸出，拼成多干。**柳杉：** three 用一根直干加 46 根近水平下垂的枝，ez 用常绿树模式。

## 接不接得上我们自己的系统

| 项 | three | ez | 说明 |
|---|---|---|---|
| 叶色随季节、秋红、冬天落叶 | 接得上 | 接得上 | 叶子是我们的卡，`setMood` 不变 |
| 积雪（`procMat` 要每顶点 `ao`） | 接得上 | 接得上 | 木头并进 `wood` 后照常 `mesh()` 烘 `ao`，图中冬昼的枝上有雪 |
| 挡路范围（`walk.posts`） | 读得出 | 读得出 | `grow()` 返回每根干的位置和根部半径；但 `site.js` 在长树之前就定了 `girth`，要从生成器读出来需要改 `site.js`，属于 #161 的范围，这次没改 |
| 种子固定、截图可重复 | 是 | 是 | 同一种子长两次，几何逐点相同 |
| 合批 | 是 | 是 | 并进现有的一份木头网格，绘制次数不变（T4 上都是 360 次） |
| 飘落物（`drift.js`） | 不受影响 | 不受影响 | 它不读树 |
| 惊鸟起飞（`flock.js` 读的柳杉） | 不受影响 | 不受影响 | 它读 `site.cedars` 的位置，位置没变 |

### T4 帧耗

首院，高档，1920×1080，秋昼，同一个 Job 里三种交替三次。Job `6afcfb24884144d2f44fa457`，`report.json` 在 `docs/t00/evidence/trees-162/t4-report.json`，site 指纹 `1634c7b` / `197e32f2…`。测量本身约 3 分钟，没有超过 20 分钟的上限。

| | 第 1 次 | 第 2 次 | 第 3 次 | 均值 |
|---|---|---|---|---|
| 现状 | 12.90 | 12.73 | 13.16 | 12.93 ms |
| three | 13.13 | 13.39 | 13.35 | 13.29 ms（+0.36） |
| ez | 12.77 | 12.97 | 13.98 | 13.24 ms（+0.31） |

三者绘制次数都是 360，三角面 194.3 万 / 194.5 万 / 195.0 万。差值在同一 Job 内的波动范围附近，可以说没有明显变慢，不能说哪个更快。

### 生成时机和包体积

- **载入时生成：** 每棵 16–33 毫秒（Node 里量），整片树林约二十棵，载入多一秒以内。建议载入时生成，不烘成 GLB 入库，省下一个要维护的文件。
- **包体积（gzip）：** three 版约 4.8 KB，ez 版约 9.0 KB，适配层约 2.6 KB。

## 业界和 GitHub 上查到的（2026-11-18，只读了检索结果的摘要）

- **three.js 自带 `TreeGenerator` / `ForestGenerator`**（[文档](https://threejs.org/docs/pages/TreeGenerator.html)）。`ForestGenerator` 是在地形上铺几十万棵实例化的「团状」远景树，不能替代院子里的近景树，最多以后用在远山。
- **ez-tree**（[GitHub](https://github.com/dgreenheck/ez-tree)，MIT），前身叫 tree-js，带一个浏览器里调参、导出 GLB 的工具。
- **proctree.js**（supereggbert），较早的单干生成器；Don McCurdy 的 glTF-Procedural-Trees 用它导出 glTF。比上面两个旧，没有试。
- **现成树模型：** 没找到 CC0 的鸡爪槭或柳杉。CGTrader、Gumroad 上有付费的鸡爪槭和雪松模型（带 glTF），许可是「免版税」，不是 CC0，能不能随开源仓库发布要逐个核，而且季节、积雪都要另接。Quaternius 等 CC0 的树是低多边形卡通风格，和 `ART-SPEC.md` 的「安静的写实」不合。所以「现成模型 + 实例化」这次不推荐。

  - 修侧枝方向的那个 bug 随手写代码一起删掉。
- **#93：**
  - 多干枫改为「几棵 TreeGenerator 斜放拼一根根脚」，调参到冠形宽平。

  - `girth("maple")` 从生成器读出来（要和 #161 协调）。
- **#94：** 树皮颜色、纵棱不受影响，照原计划做在 `M.bark` 上。
