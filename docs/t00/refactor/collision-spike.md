# 走路、挡路、镜头遮挡从画出来的网格算：试验报告（#161）

> 状态：试验的结论稿。数字在分支 `claude/collision-spike-161` 的提交上量，每节写明是哪个提交（对照、edges、eye、Recast 在 **880aa04**；T4 在 **038a60a**）。
> 试验代码在 `tools/spike/`（Node 侧）和 `app/src/spike/`（新 walker 本身，页面和 Node 共用），外加 `app/yard.js` 两行（`?walker=mesh` 换上新 walker、给每次查询计时）和 `tools/gpu/job.cjs` 的一个选项（边走边量）。这些都只在分支上，**不合入 main 的 `app/`**。`walk` 数据和现有测试一条未动。

## 结论先说

**推荐：换，但不是换成任何一个现成的「角色控制器」或「导航网格」库，而是用 three-mesh-bvh 做网格查询，自己烘一张 5 厘米的可走格子（做法照 Recast：地面高度、净空、台沿、按身体外廓收边、从入口洪水填充剔掉走不到的），在构建时烘好随站点发出，运行时只查表。** Recast 留作寻路的候选，不用它的可走面。理由：

1. 现在的五个已知 bug 里，两个在新做法下**不用写一行补丁就没了**（#148 台基四周走不过去、#154 点地走不出来——所有者报的那个点在新做法下本来就不挡），第三个（#149 殿内柱）在新做法下**不可能发生**（画了柱就挡）。另外查出两个旧数据里没人报过的：**铜香炉根本没登记，他能直接穿过去**；枫树露出地面的根，旧数据也让他踩进去。
2. **`edges` 跑在新 walker 上，膝盖以上全场 0 处**（大殿、茶寮、禅堂都 0）。膝盖以下只剩一棵杉树露出地面的根，12 个站位、最深 8.2 厘米。旧数据用一个 `BODY`、`edges` 用一条外廓，两份对不齐；新做法里两者是同一条外廓。
3. 体积小：three-mesh-bvh gzip 后 **17 KB**（MIT）；接进页面后主包 gzip 从 440.8 KB 变成 460.4 KB，**多 19.6 KB**。Recast 224 KB，Rapier 1.1–1.6 MB，后两者都过了 issue 定的 300 KB 线或贴着线。
4. Node 里照样跑：同一份网格在 Node 里建 BVH 1.1–1.3 秒，烘格子 5.7–6.1 秒（只第一次，之后按三角形的哈希读缓存，11 毫秒）。现有单测原样跑在新 walker 上，用到 walker 的 19 个文件 142 条里，新 walker 用 0.38 圆柱时 **131 条直接通过**、用真实外廓时 129 条，没过的逐条有解释（第五节、附表），其中多数是断言写死了旧模型（「`r + BODY − 0.02` 处必须挡住」「台面正好 0.45」）。
5. 运行时便宜：`blocked` 查表 0.8–2 µs，`heightAt` 一条射线约 3 µs，`eyeShut` 4.0 µs（旧 2.2 µs）。

不推荐的两条现成路：

- **Rapier 角色控制器**：自己会爬台阶、贴墙滑、跳上矮台，手感是物理的；但 gzip 后 1.1 MB（拆分 wasm 版）到 1.6 MB（内嵌 wasm 版），每步 166 µs（含 `world.step`），要把「他」改成胶囊体并接管 `stride`、跳、落地，改动面最大，还解决不了镜头和寻路。
- **Recast 的可走面**：烘得快（同一份 20.8 万三角形 0.66 秒，比我们 JS 烘快七八倍），寻路 0.1–1 ms；但它**把台沿上下两侧都往里收一个身体半径**，茶寮、禅堂一米来宽的前廊和台基的侧边几乎收没（图 `recast-vs-grid.png` 红色），旧数据和新格子都让他站到台沿边上（跳下要求他离台沿 0.65 米以内）。这在 Recast 里不能单边配置。它也不剔走不到的面（殿内空壳整块算可走，图中蓝色），要自己按连通性剔。

所以迁移的形状是：**格子当可走面，BVH 当镜头和射线，寻路先沿用 `route.js`（它本来就是在格子上的 A*，只是格子来源换了），以后要更快再接 Recast 的 Detour 或在格子上做层次 A*。**

## 一、做了什么（验收 1）

`app/src/spike/meshwalker.js` 的 `createMeshWalker` 与 `createWalker` 同形：`heightAt / blocked / onGround / floorAt / eyeShut`，以及 `eyeAt / landAt / onStairs / wall / railNear / setRoom / setLoft / room / loft`。数据只来自画出来的网格：`buildSite` 的 `site.root`、`trees.js` 的树、`props.js` 的香炉、`interior.js` 的房间、`ground.js` 位置上的一张平铺地面（Node 里没有画布，用同尺寸平面代）。试验区域外、上凌霄阁、进别的殿，它把问题交回旧 walker（`fallback`）。`yard.js` 的调用方式不变：`tools/spike/swap.mjs` 是一个 Node 加载钩子，把每一处 `import … from "app/src/site.js"` 换成 `site-swap.mjs`，其中只有 `createWalker` 换了；所以现有单测和 `tools/edges.mjs` 不改一字就跑在新 walker 上。

| 问题 | 怎么问网格 |
|---|---|
| `heightAt` | 从层的天花（首院取 3.0 米：高过大殿台基 1.5 米，低过最低的檐 3.54 米）往下一条射线，第一个朝上的面（法线 y > 0.5）就是地；标成「绕着走」的东西（蒲团、矮茶案）不算地，射线穿过去。 |
| `blocked` | 查烘好的格子（下面）。 |
| `floorAt` / `onGround` / `onStairs` | 地面射线停下那个面的材质：`paving` → 院子，带 wood → 木，`steps` → 台阶（`path`），其余 → 石。 |
| `eyeShut` | 离任何面 12 厘米内；或者脚下是走不到的格子（殿身、墙身、台基身），且眼在那一处最高的面以下；或者四面和头上都被围住。 |
| `railNear` | 一个球内有不朝上的面（地面不算），且在头高以下。 |
| `wall` | 15 厘米内有东西，或在封闭实体内（向 +x 的射线先碰到背面）。 |

**烘格子**（`bake`，照 Recast 的做法，但在 JS 里、对我们的规矩做了两处不同）：

1. 每格地面高度：上面的射线。
2. 每格收集**从它自己的地面往上**立着的东西（半径一格对角线的一半，即 3.5 厘米；朝上的面是地面，不收），记下它占的绝对高度范围。标成「绕着走」的东西从地面起就算。
3. 台沿：邻格地面比本格高出 `CLIMB`（0.25 米：比任何一级踏步 0.10–0.19 高，比最矮的台基 0.30 低）以上，本格（台下那格）是边界，高度范围从本格地面到邻格地面。同一格既有矮东西又是台沿，两段高度取并集。踢面、台基侧面、墙裙这类「在别人地面下面」的东西都按台沿处理。
4. 收边：对每个边界格周围 `BODY` 内的每个格子，**按站人那一格的地面**量这个边界占的高度（若边界格的地面是他一步跨得上去的，比如上一级踏步，就按那一级量），取其中高过 `CLIMB`、低于 `CLEAR`（1.45 米）的那段，查**他在那段高度上的外廓半径**；距离小于这个半径就关掉。外廓不是一根粗 0.38 米的圆柱，而是 `tools/edges.mjs` 的 `outline()` 从两个身体模型、六种姿势量出来的每 5 厘米高度上的最大伸出（`app/src/spike/outline.json`：脚边 0.34，腰下袖口 0.38，胸口以上 0.14–0.20）。所以台基侧面不挡站在台面上的人，台阶的踢面不挡踩在下一级上的人（Recast 两侧都收，这是不同之处）。
5. 洪水填充：从院子中央（殿内从门内一步）出发，八向、地面差不超过 `CLIMB`，填不到的格子也关掉（殿身空壳、桌面、栏杆顶）。

`SPIKE_BODY=cylinder` 把外廓换回旧数据的「处处 0.38」，用来把「身体用什么形状」和「几何从哪来」两件事分开看。

## 三、他的宽度（验收 3）

- 新做法里的「他」就是 `edges.mjs` 量出来的那个旋转体，不再是一根 0.38 米的圆柱：烘格子时，每个挡路的东西都按它相对于他脚下的高度，取他在那个高度上伸出多远。
- 用外廓比用圆柱多出 4 m² 能走的地方，主要是胸口高度的东西（禅堂前廊的格扇、柱身中段）：他在那个高度只伸出 0.14–0.20 米。
- **`pnpm run edges` 换新 walker 跑**（提交 880aa04，`node --import ./tools/spike/swap.mjs tools/edges.mjs`，3 分钟；输出存在 `edges-new-walker.txt`）：**膝盖以上，全场每座建筑都是 0 处超限**，试验区里的大殿、茶寮、禅堂也都是 0。膝盖以下只剩一处：首院西南角那棵杉树（−19.6, 0.5）画出来的根，离地 0.11 米，比一级踏步还矮，新做法把它当成可以踩上去的地面，`edges` 却说他的鞋会踩进根里，12 个站位，最深 8.2 厘米。补法是把树根挂上「绕着走」的标记，或者让膝盖以下用 `outline.low`（鞋和袍摆）单独收一圈。旧数据在这里没有超限，因为它用一个写大了的圆把树根整个围住了。
- 这个结论**比旧数据更严**：旧数据在 `edges` 上过，靠的是写得宽的矩形和圆；新做法在 `edges` 上过，靠的是画出来的形状和同一条外廓。格子化带来的误差最多是一个格子对角线的一半（3.5 厘米）：`edges.test.mjs` 里禅堂后角柱那一条差 1 厘米，就是这个误差。

## 五、镜头（验收 5）

`eaves`、`sweeps`、`follow`、`director` 四组单测原样跑在新 walker 上（提交 880aa04，外廓和圆柱结果相同）：**27 条过 24 条**。

- `eaves`、`sweeps` 全过（观音殿、各殿檐下、台沿跳下落点）。
- `follow`「绕首院一圈镜头不跳」：一帧里眼的高度自己变了 0.06 米，在 (−10.8, 7.9)。原因是 `eyeAt` 我用的是周围五点地面平均，碰上了树下土堆和台沿；旧的 `eyeAt` 只在台阶上取斜坡。要另做一个「沿走过的路平滑」的 `eyeAt`，不是网格的问题。
- `follow`「沿中轴到大殿台阶」：测试写的路线穿过 (0, 14.19)，离香炉中心 1.19 米；**旧数据没有香炉，这条路线本身就穿过香炉的炉沿**。路线要绕开香炉。
- `director`「茶 从 30° 转过去」：找不到绕他的镜头路线。新的 `railNear` 把茶桌、凳子、树都算作「要离开 12 厘米」，比旧的（只算栏杆）严，绕路时可走的点不够。要么 `railNear` 只认标成栏杆的东西，要么转场的搜索放宽；这是要定的口径。

另在首院按 25 厘米、离地七个高度，共 30 万点比了 `eyeShut`（提交 880aa04，`eye.json`）：

| 离地 | 两边都关 | 两边都开 | 只有旧的关 | 只有新的关 |
|---|---|---|---|---|
| 0.4 m | 17407 | 22952 | 1684 | 901 |
| 1.8 m | 12537 | 24642 | 4732 | 1033 |
| 3.6 m | 11098 | 26084 | 5133 | 629 |
| 7.0 m | 11313 | 24365 | 7038 | 228 |

「只有旧的关」最多的几类：旧数据把**整座殿的 `solids`（含台基侧面、背面）上方 5.5 米**都关了，而新做法里台基侧面已经能走，眼也就能在那里；**檐下梁架、瓦之间的空隙**（旧数据按 `walk.roofs` 从梁底到屋脊整块关掉，新做法只看离面 12 厘米）。后者是新做法真的放松了的地方：要么保留由 `building.js` 参数算出来的 `walk.roofs`（它不是手对的，是生成的），要么对每个屋顶取凸包。**建议保留 `roofs`。**

## 六、寻路（验收 6）

- **`route.js` 原样用新 walker**：`route.test` 全过，包括「从每个前廊两端、茶案和蒲团旁，到院子的 234 条路线」和「所有者报的那个点（茶寮南端 −12.85, 5.98）走出来」——后者的前提「这个点是挡着的」在新做法下不成立了：**这个点本来就不该挡**，#154 的根因在新做法下没有。
- **Recast**（`recast.json`）：同一份三角形，cs 5 厘米，烘 0.66 秒，397 个多边形；寻路四条（茶寮南端到院子、院子到大殿前廊、茶寮到禅堂、院子到大殿台基侧面）各 0.08–1.0 ms；站点查询 1.3 µs。缺点见「结论」：两侧收边、不剔不连通的面。
- **能不能把 `route.js` 和 `director.wayRound` 合成一份**：能，而且新做法让这件事更自然。两者都是「在一张格子上 A* 再拉直」，差别只在格子的来源（前者问 `blocked`，后者问 `inWay`）和高度（前者在脚下，后者在眼的高度）。烘好的格子给前者；后者的「眼能不能在这」本来就要对网格打射线。合成后是一个 `gridSearch(open(i, j), cost, budget)` 的生成器，两边各传自己的 `open`。这一步不依赖换不换网格，可以先做。

## 八、性能（验收 8）

**包体积**（`sizes.json`：用同一个 Vite 打包各库的最小用法，再 gzip −9）：three-mesh-bvh **17 KB**；recast-navigation 224 KB（其中 wasm 215 KB）；Rapier 内嵌 wasm 的版本 1607 KB，wasm 单独发的版本光 wasm 就 1141 KB。把新 walker 真接进页面后（提交 038a60a），主包 gzip 从 440.8 KB 变成 460.4 KB，**多 19.6 KB**，远低于 300 KB 的线。

**T4**（提交 038a60a，Job `20261118-001241`；`report.json` 带 site 指纹，存为 `t4-report.json`，entry `assets/index-0SF3KxB2.js`，sha256 `a0e32aef…`；spec 存为 `t4-spec.json`）。量法照 `geometry-budget.md`「五之二」：同一个 Job 里旧、新交替，各量三次。页面从 `?cam=0,25,0,0&enter` 进去，交给 `__walk` 一条穿过首院的路线，计 6 秒的帧。`__cost(40)` 是只算画、不算浏览器呈现的每帧毫秒数；「walker」一列是这 6 秒里每帧花在 walker 所有查询上的毫秒数（`?walker=mesh` 时由 `app/src/spike/page.js` 计时，旧 walker 也走同一层计时）。

| | `__cost` 中位数（范围） | walker 每帧中位数（范围） | 载入中位数 |
|---|---|---|---|
| 高档 1080p，旧 | 11.16 ms（10.73–11.21） | 0.315 ms（0.306–0.327） | 9.0 s |
| 高档 1080p，新 | 10.98 ms（10.95–11.24） | 0.354 ms（0.327–0.391） | 18.6 s |
| 低档 390×844@3，旧 | 4.77 ms（4.70–4.78） | 0.315 ms（0.295–0.349） | 8.5 s |
| 低档 390×844@3，新 | 5.01 ms（4.90–5.03） | 0.338 ms（0.336–0.343） | 18.1 s |

- **每帧**：walker 的查询多花 **0.02–0.04 ms**（低档 +0.02，高档 +0.04），远低于 0.5 ms 的线。画一帧的耗时，高档差 −0.18 ms，低档差 +0.24 ms，都在三次各自的范围里，是噪声；新 walker 不往 GPU 加东西。每帧约 70–120 次查询，大头是跟拍镜头的 `eyeShut`。
- **载入**：多出的 9–10 秒全是**在页面里现烘格子**（8.6–9.0 s；收集三角形加建 BVH 0.78–0.83 s）。这是最坏的情况。方案里格子在构建时烘好随站点发出，载入时只多收集三角形、建 BVH 这 0.8 秒；这一步还可以再省：直接用 `mergeStatic` 合好的几何，或者把 BVH 序列化随格子一起发。
- **没量准的**：交给 `__walk` 的路线第一段在 (−4.8, 13.6) 被挡住，新旧六次都停在同一点（所以两边能比）。后几秒他在原地反复试 `stride`，walker 照样被查，但这段不是「一路走过首院」的典型负载。T4 上的 CPU 是云主机的，不是手机：手机上每帧的 walker 时间按经验要乘 3–5，也就是 0.1–0.2 ms 的增量，仍在线内；手机上现烘格子要几十秒，所以**必须是构建时的产物**。

**本地 SwiftShader**（同一脚本，480×270，低档，用来跑通流程）：旧 walker 每帧 0.36 ms，新 0.42 ms；载入多 5.0 s（烘格子 6.0 s，收集加建 BVH 0.73 s）。

## 九、迁移方案（验收 9）

每一步 main 全绿，每一步都可单独回退。估计 **6 个 PR**。

1. **合并两个寻路**（不依赖网格）：`route.js` 与 `director.wayRound` 共用一个格子 A* 生成器。删掉一份搜索代码。
2. **构建时烘格子**：`tools/bake-walk.mjs` 在 Node 里建场景、建 BVH、烘格子，写 `app/shared/walk/<level>.bin`（随 `KEPT` 拷进 `dist/`），按三角形哈希命名；`pnpm build` 和单测在哈希不符时重烘。加单测：格子与当前几何同哈希。页面和单测都只读文件。此时还不用它。
3. **新 walker 上线于首院**，旧 walker 作回退（与本试验的 `fallback` 一样），`?walker=old` 可切回。在画的地方补上意图标记：蒲团、矮茶案、香台挂 `userData.walk = "post"`；门挂 `userData.door = hallId`（`blocked` 在门线挡住，与现在一样由门的触发器进殿）。改掉写死旧模型的断言（`r + BODY − 0.02` 改成「`edges.outline` 在那个高度的伸出」，台面 0.45 改成「与画出来的台面同高」）。修香炉。#148 的台基绕行、#154 的点地在这一步自然得到。
4. **全场**：其余两层台地、山路、凌霄阁的回廊（多层：格子按层存，`setLoft` 选层）、八间殿内。删 `walk.solids / decks / ramps / posts`，删 `createWalker` 里对应的 150 行。`walk.drops` 改由格子派生。
5. **镜头**：`eyeShut` 改为 BVH 射线 + 格子；`railNear` 定口径；`eyeAt` 改为沿路平滑。`walk.roofs` 保留（它由 `building.js` 参数生成，不是手对的），雪的遮蔽 `shelter.js` 照旧用它。
6. **工具和测试**：`edges.mjs` 的「先洪水再量身体」变成「读格子再量身体」（同一份外廓），大约减半；`edge-coverage.md` 的表照出。`sweeps`、`nearplane`、`standing` 改成对 BVH 打射线（`eaves.test` 已经这么做，只是对一座殿）。

**仍要手写的**（都是意图，不是几何）：这是一扇能进的门（`site.halls` 的 `door/out/outYaw`）；这是一个座位（`site.seats`）；这是一件绕着走、不许踩的东西（`userData.walk = "post"`）；这是一处要点的地方（`site.places`）；层与入口（格子洪水的种子、凌霄阁的层）；`walk.roofs`（生成的，保留）；`shade`（地面阴影，生成的，保留）。
**可以删的**：`walk.solids / decks / ramps / posts`（约 277 个柱、61 块实体、31 块台面、16 段台阶）、`walk.rails`、手写的 `walk.drops`；`createWalker` 的大部分；`edges.mjs` 里为守 `walk` 数据而有的「每个零件归哪座殿」那部分可以保留做报告，但不再是守门。
