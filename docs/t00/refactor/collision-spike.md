# 走路、挡路、镜头遮挡从画出来的网格算：试验报告（#161）

> 状态：试验的结论稿。数字在分支 `claude/collision-spike-161` 的提交上量，每节写明是哪个提交（对照、edges、eye、Recast 在 **880aa04**；T4 在 **038a60a**）。
> 试验代码在 `tools/spike/`（新 walker 是 `tools/spike/meshwalker.mjs`，Node 里用），外加 `tools/gpu/job.cjs` 的一个选项（边走边量）。把它接进页面量 T4 用的完整代码——`app/src/spike/`、`app/yard.js` 两行（`?walker=mesh` 换上新 walker、给每次查询计时）、Rapier 和 Recast 两个量测依赖——留在只读分支 `claude/collision-spike-161-page`（提交 1eba311），**不进 main 的 `app/`**。本 PR 不改 `app/`；`walk` 数据和现有测试一条未动；新依赖只有开发依赖 three-mesh-bvh（工具用，不进站点包）。

## 结论先说

**推荐：换，但不是换成任何一个现成的「角色控制器」或「导航网格」库，而是用 three-mesh-bvh 做网格查询，自己烘一张 5 厘米的可走格子（做法照 Recast：地面高度、净空、台沿、按身体外廓收边、从入口洪水填充剔掉走不到的），在构建时烘好随站点发出，运行时只查表。** Recast 留作寻路的候选，不用它的可走面。理由：

1. 现在的五个已知 bug 里，两个在新做法下**不用写一行补丁就没了**（#148 台基四周走不过去、#154 点地走不出来——所有者报的那个点在新做法下本来就不挡），第三个（#149 殿内柱）在新做法下**不可能发生**（画了柱就挡）。另外查出两个旧数据里没人报过的：**铜香炉根本没登记，他能直接穿过去**；枫树露出地面的根，旧数据也让他踩进去。
2. **`edges` 跑在新 walker 上，膝盖以上全场 0 处**（大殿、茶寮、禅堂都 0）。膝盖以下只剩一棵杉树露出地面的根，12 个站位、最深 8.2 厘米。旧数据用一个 `BODY`、`edges` 用一条外廓，两份对不齐；新做法里两者是同一条外廓。
3. 体积小：three-mesh-bvh gzip 后 **17 KB**（MIT）；接进页面后主包 gzip 从 440.8 KB 变成 460.4 KB，**多 19.6 KB**。Recast 224 KB，Rapier 1.1–1.6 MB，后两者都过了 issue 定的 300 KB 线或贴着线。
4. Node 里照样跑：同一份网格在 Node 里建 BVH 1.1–1.3 秒，烘格子 5.7–6.1 秒（只第一次，之后按三角形的哈希读缓存，11 毫秒）。现有单测原样跑在新 walker 上，用到 walker 的 19 个文件 142 条里，新 walker 用 0.38 圆柱时 **131 条直接通过**、用真实外廓时 129 条，没过的逐条有解释（第五节、附表），其中多数是断言写死了旧模型（「`r + BODY − 0.02` 处必须挡住」「台面正好 0.45」）。
5. 运行时便宜：`blocked` 查表 0.8–2 µs，`heightAt` 一条射线约 3 µs，`eyeShut` 4.0 µs（旧 2.2 µs）。

不推荐的两条现成路：

- **Rapier 角色控制器**：自己会爬台阶、贴墙滑、跳上矮台，手感是物理的；但 gzip 后 1.1 MB（拆分 wasm 版）到 1.6 MB（内嵌 wasm 版），每步 166 µs（含 `world.step`），要把「他」改成胶囊体并接管 `stride`、跳、落地，改动面最大，还解决不了镜头和寻路。
- **Recast 的可走面**：烘得快（同一份 20.8 万三角形 0.66 秒，比我们 JS 烘快七八倍），寻路 0.1–1 ms；但它**把台沿上下两侧都往里收一个身体半径**，茶寮、禅堂一米来宽的前廊和台基的侧边几乎收没（图 `recast-vs-grid.png` 红色），旧数据和新格子都让他站到台沿边上（跳下要求他离台沿 0.65 米以内）。这在 Recast 里不能单边配置。它也不剔走不到的面（殿内空壳整块算可走，图中蓝色），要自己按连通性剔。

所以迁移的形状是：**格子当可走面，BVH 当镜头和射线，寻路先沿用 `route.js`（它本来就是在格子上的 A*，只是格子来源换了），以后要更快再接 Recast 的 Detour 或在格子上做层次 A*。**

## 一、做了什么（验收 1）

`tools/spike/meshwalker.mjs` 的 `createMeshWalker`（页面版在 `claude/collision-spike-161-page` 的 `app/src/spike/meshwalker.js`，同一份代码） 与 `createWalker` 同形：`heightAt / blocked / onGround / floorAt / eyeShut`，以及 `eyeAt / landAt / onStairs / wall / railNear / setRoom / setLoft / room / loft`。数据只来自画出来的网格：`buildSite` 的 `site.root`、`trees.js` 的树、`props.js` 的香炉、`interior.js` 的房间、`ground.js` 位置上的一张平铺地面（Node 里没有画布，用同尺寸平面代）。试验区域外、上凌霄阁、进别的殿，它把问题交回旧 walker（`fallback`）。`yard.js` 的调用方式不变：`tools/spike/swap.mjs` 是一个 Node 加载钩子，把每一处 `import … from "app/src/site.js"` 换成 `site-swap.mjs`，其中只有 `createWalker` 换了；所以现有单测和 `tools/edges.mjs` 不改一字就跑在新 walker 上。

| 问题 | 怎么问网格 |
|---|---|
| `heightAt` | 从层的天花（首院取 3.0 米：高过大殿台基 1.5 米，低过最低的檐 3.54 米）往下一条射线，第一个朝上的面（法线 y > 0.5）就是地；标成「绕着走」的东西（蒲团、矮茶案）不算地，射线穿过去。 |
| `blocked` | 查烘好的格子（下面）。 |
| `floorAt` / `onGround` / `onStairs` | 地面射线停下那个面的材质：`paving` → 院子，带 wood → 木，`steps` → 台阶（`path`），其余 → 石。 |
| `eyeShut` | 离任何面 12 厘米内；或者脚下是走不到的格子（殿身、墙身、台基身），且眼在那一处最高的面以下；或者四面和头上都被围住。 |
| `railNear` | 一个球内有不朝上的面（地面不算），且在头高以下。 |
| `wall` | 15 厘米内有东西，或在封闭实体内（向 +x 的射线先碰到背面）。 |

**烘格子**（`bake`，照 Recast 的做法，但在 JS 里、对我们的规矩做了两处不同）：

1. 每格地面高度：上面的射线。
2. 每格收集**从它自己的地面往上**立着的东西（半径一格对角线的一半，即 3.5 厘米；朝上的面是地面，不收），记下它占的绝对高度范围。标成「绕着走」的东西从地面起就算。
3. 台沿：邻格地面比本格高出 `CLIMB`（0.25 米：比任何一级踏步 0.10–0.19 高，比最矮的台基 0.30 低）以上，本格（台下那格）是边界，高度范围从本格地面到邻格地面。同一格既有矮东西又是台沿，两段高度取并集。踢面、台基侧面、墙裙这类「在别人地面下面」的东西都按台沿处理。
4. 收边：对每个边界格周围 `BODY` 内的每个格子，**按站人那一格的地面**量这个边界占的高度（若边界格的地面是他一步跨得上去的，比如上一级踏步，就按那一级量），取其中高过 `CLIMB`、低于 `CLEAR`（1.45 米）的那段，查**他在那段高度上的外廓半径**；距离小于这个半径就关掉。外廓不是一根粗 0.38 米的圆柱，而是 `tools/edges.mjs` 的 `outline()` 从两个身体模型、六种姿势量出来的每 5 厘米高度上的最大伸出（`tools/spike/outline.json`：脚边 0.34，腰下袖口 0.38，胸口以上 0.14–0.20）。所以台基侧面不挡站在台面上的人，台阶的踢面不挡踩在下一级上的人（Recast 两侧都收，这是不同之处）。
5. 洪水填充：从院子中央（殿内从门内一步）出发，八向、地面差不超过 `CLIMB`，填不到的格子也关掉（殿身空壳、桌面、栏杆顶）。

`SPIKE_BODY=cylinder` 把外廓换回旧数据的「处处 0.38」，用来把「身体用什么形状」和「几何从哪来」两件事分开看。

## 三、他的宽度（验收 3）

- 新做法里的「他」就是 `edges.mjs` 量出来的那个旋转体，不再是一根 0.38 米的圆柱：烘格子时，每个挡路的东西都按它相对于他脚下的高度，取他在那个高度上伸出多远。
- 用外廓比用圆柱多出 4 m² 能走的地方，主要是胸口高度的东西（禅堂前廊的格扇、柱身中段）：他在那个高度只伸出 0.14–0.20 米。
- **`pnpm run edges` 换新 walker 跑**（提交 880aa04，`node --import ./tools/spike/swap.mjs tools/edges.mjs`，3 分钟；输出存在 `edges-new-walker.txt`）：**膝盖以上，全场每座建筑都是 0 处超限**，试验区里的大殿、茶寮、禅堂也都是 0。膝盖以下只剩一处：首院西南角那棵杉树（−19.6, 0.5）画出来的根，离地 0.11 米，比一级踏步还矮，新做法把它当成可以踩上去的地面，`edges` 却说他的鞋会踩进根里，12 个站位，最深 8.2 厘米。补法是把树根挂上「绕着走」的标记，或者让膝盖以下用 `outline.low`（鞋和袍摆）单独收一圈。旧数据在这里没有超限，因为它用一个写大了的圆把树根整个围住了。
- 这个结论**比旧数据更严**：旧数据在 `edges` 上过，靠的是写得宽的矩形和圆；新做法在 `edges` 上过，靠的是画出来的形状和同一条外廓。格子化带来的误差最多是一个格子对角线的一半（3.5 厘米）：`edges.test.mjs` 里禅堂后角柱那一条差 1 厘米，就是这个误差。

## 五、镜头（验收 5）

`eaves`、`sweeps`、`follow`、`director` 四组单测原样跑在新 walker 上（提交 880aa04，外廓和圆柱结果相同）：**27 条过 24 条**。

- `eaves`、`sweeps` 全过（观音殿、各殿檐下、台沿跳下落点）。
- `follow`「绕首院一圈镜头不跳」：一帧里眼的高度自己变了 0.06 米，在 (−10.8, 7.9)。原因是 `eyeAt` 我用的是周围五点地面平均，碰上了树下土堆和台沿；旧的 `eyeAt` 只在台阶上取斜坡。要另做一个「沿走过的路平滑」的 `eyeAt`，不是网格的问题。
- `follow`「沿中轴到大殿台阶」：测试写的路线穿过 (0, 14.19)，离香炉中心 1.19 米；**旧数据没有香炉，这条路线本身就穿过香炉的炉沿**。路线要绕开香炉。
- `director`「茶 从 30° 转过去」：找不到绕他的镜头路线。新的 `railNear` 把茶桌、凳子、树都算作「要离开 12 厘米」，比旧的（只算栏杆）严，绕路时可走的点不够。要么 `railNear` 只认标成栏杆的东西，要么转场的搜索放宽；这是要定的口径。

另在首院按 25 厘米、离地七个高度，共 30 万点比了 `eyeShut`（提交 880aa04，`eye.json`）：

| 离地 | 两边都关 | 两边都开 | 只有旧的关 | 只有新的关 |
|---|---|---|---|---|
| 0.4 m | 17407 | 22952 | 1684 | 901 |
| 1.8 m | 12537 | 24642 | 4732 | 1033 |
| 3.6 m | 11098 | 26084 | 5133 | 629 |
| 7.0 m | 11313 | 24365 | 7038 | 228 |

「只有旧的关」最多的几类：旧数据把**整座殿的 `solids`（含台基侧面、背面）上方 5.5 米**都关了，而新做法里台基侧面已经能走，眼也就能在那里；**檐下梁架、瓦之间的空隙**（旧数据按 `walk.roofs` 从梁底到屋脊整块关掉，新做法只看离面 12 厘米）。后者是新做法真的放松了的地方：要么保留由 `building.js` 参数算出来的 `walk.roofs`（它不是手对的，是生成的），要么对每个屋顶取凸包。**建议保留 `roofs`。**

## 六、寻路（验收 6）

- **`route.js` 原样用新 walker**：`route.test` 全过，包括「从每个前廊两端、茶案和蒲团旁，到院子的 234 条路线」和「所有者报的那个点（茶寮南端 −12.85, 5.98）走出来」——后者的前提「这个点是挡着的」在新做法下不成立了：**这个点本来就不该挡**，#154 的根因在新做法下没有。

**1. 谁还在读旧的 `walk` 数据**（`grep` 了 `app/` 里对 `walk.*`、`site.shade`、`floorAt`、`railNear`、`eyeShut` 的每一处）

| `drop.js`（`findDrop/findClimb/seatHop`） | `walk.drops`，加 walker | **跟着换**：台沿由格子派生，形状不变，这两个函数不改 |

| `shelter.js`（雪的遮蔽图）、`rites.js` 收尾镜头挑屋顶 | `walk.roofs` | **留着**：由 `building.js` 按参数生成，不是手对的 |

| `yard.js` 的 `pickFloor` | `walker.heightAt` | **跟着换**，不用改代码：沿视线往前推，推到地面以下为止；新的 `heightAt` 是画出来的地面 |
| 座位 | `site.seats` | **留着**（意图），但加一条单测对上画出来的坐具 |
| `building.js`、`geo.js` | 生成 `walk.*` | 迁移完删掉生成走路数据的那部分，`roofs` 和 `shade` 留着 |

**2. 网格表达不了的意图怎么写。** 要打标签，这确实是一份新的描述。但它和旧数据不是一类东西：标签挂在画它的那一行上，不另写坐标，形状仍然只有网格一份。需要的标签：

| 标签 | 用在哪 | 谁保证不漏 |
|---|---|---|
| `userData.walk = "post"` | 要绕着走、不许踩的矮物件：蒲团、矮茶案、香台、（若定）树根 | 单测：遍历用 `CUSHION`、`STOOL` 轮廓画的网格，以及高度低于 `CLIMB`、又不是台阶或门槛的独立小网格，没挂标签就报 |
| `userData.walk = "off"` | 画了但不是实物的：雾片、光柱、烟、透明的叶片。这些现在按材质（透明、`alphaTest`、`ShaderMaterial`）自动排除 | 自动排除；新材质由 `edges`、`nearplane` 兜底 |
| `userData.door = hallId` | 能进的门：格子在门线挡住，进殿仍由触发器管 | 单测：`site.halls` 每扇门都有一个挂了标签的网格 |
| `userData.eyeOnly = true` | 只挡镜头、不挡人的东西（比如梁架之间的空当若要整块挡住） | 现在不需要：`walk.roofs` 已经管这件事。将来要用再加单测 |

其余三件不用标签，属于结构：
- **凌霄阁的平坐**：格子按层存，`setLoft` 选层，和现在的 `walk.decks` 的 `loft` 字段同义。
- **殿内房间**：每间房一张格子（试验里大殿殿内就是这么做的），`setRoom` 选格子。
- **台沿外 0.5 米那一圈**：它现在是 `findClimb` 自己的规矩（从 0.5 米外起跳），不是走路数据，不受影响。

**3. 多层。** 试验里的格子是**单层高度图**：每格一个地面，取天花以下第一个朝上的面。首院的天花设在 3.0 米（高过台基 1.5 米，低过最低的檐 3.54 米），所以檐下、台上台下在这里都不重叠。重叠的地方只有凌霄阁（楼上楼下）和殿内（院子下 60 米，各自一张格子）。办法照 Recast 的「层」：同一 (x, z) 存多层，每层有自己的天花，`setLoft`、`setRoom` 选层。只多存平坐那一层，体积可以不计。凌霄阁没做，未验。

**4. 装饰改动会悄悄改走路**（加一根角梁、一段树根、一只香炉，都可能关掉一条路）。做法：CI 里跑 `tools/bake-walk.mjs`，拿新格子和 main 上的格子比，报告三件事：① 可走面积变了多少 m²，按建筑分；② `site.places`、`site.seats`、每扇门的站位、`site.views` 里有没有哪个从入口走不到了；③ 差异图作为构建产物上传。②出现就算失败，①超过某个阈值（比如 1 m²）在 PR 评论里列出来。耗时：试验区烘一次 6 s（Node，JS），全场约 20 s；改用 Recast 体素化取高度场可以快七八倍。这件事旧做法做不到：旧数据和画面对不齐，改装饰根本不会报。

**4 之二. 这项检查排在第几步**（主创问）：排在**迁移第 2 步**，也就是构建时烘格子那个 PR，和烘格子同一个 PR 落地，在新 walker 默认启用（第 3 步）之前。理由：它只需要「能在 Node 里烘出格子」，不需要页面用上新 walker；早放进 CI，第 3 步以后每个 PR 都有人看着可走面积。它也能反过来看旧 walker：在旧 walker 上做同样的洪水填充，旧数据被改动时一样报。耗时：全场冷烘约 20 s（JS；有缓存时只读文件，十几毫秒），比较和出图约 2 s。放在 `verify` 里每次推送都跑，不放进夜里的全量。第 1 步（合并两个寻路）不依赖它，可以并行。

**5. 对另两条试验的要求**
- **#162 换树**：树的几何在 Node 烘焙时和浏览器里必须一模一样（同种子、同参数、同一份代码或同一个文件），否则树干和格子对不上。验法：烘焙时把树的三角形指纹写进格子文件，页面载入后比一次，对不上就在控制台报错，单测也比。被风吹动的部分（叶、枝梢）不进碰撞，只取树干和露出地面的根。
- **#163 换小沙弥**：`tools/spike/outline.json`（他在每个高度上伸出多远）要从新模型重新量（`node tools/spike/outline.mjs`，就是 `edges.mjs` 的 `outline()`），量完重烘格子；格子文件名带上外廓的指纹，外廓一变就重烘。`BODY` 这个常数只剩下作为外廓最大值的意义。

**5 之二. 杉树根那 12 个站位怎么补**（主创问：改几何、改标签还是改外廓，哪种不产生第二份描述）。

- **改外廓（推荐）**：膝盖以下改用 `edges.mjs` 已经量出来的 `outline.low`（鞋和袍摆，侧向 0.20–0.32 米），并且把 `CLIMB` 以下、不是一整片能踩的地面的东西也算进障碍：一个格子里有立着的面、高出地面 2 厘米以上、又不在一片连通的可踩面里（树根、柱础边、门槛端头），按 `outline.low` 在那个高度的伸出收边。这只是把「他有多宽」这条曲线从膝盖以上延到膝盖以下，`edges` 量的也正是这条曲线，**不产生第二份描述**。代价是要在烘焙里多分一种「低处的立面」，并证明台阶的踢面不被它误挡（踢面上面是连着的踏面，可以按这个排除）。未实现，未验。
- **改标签**：给树根挂 `userData.walk = "post"`。只是在画它的网格上加一个标记，不另写坐标，严格说不算第二份描述；但它让「树根不许踩」变成一条要人记得的规矩，以后每换一次树（#162）都得记得挂。不推荐作为长久办法。
- **改几何**：把根画得贴地（不高出 2 厘米）。这改的是画面，为了碰撞去改画面，违背「画面第一」，不推荐。

**6. 玩家**
- **已存的位置**（`yunjing.place.v1`）**和分享出去的 `?cam` 地址**，可能落在新挡住的格子里。现在 `yard.js` 对 `?cam` 只往外挪最多 6 厘米；`route.js` 的 `nearestOpen` 能从挡住的点退出来（#154 的修复）。迁移时把这两处统一成：载入时如果落在挡住的格子里，就挪到 0.5 米内最近的、从入口走得到的格子；0.5 米内没有，就回到起点。未验。
- **跳上台的余量**：旧数据台高 0.45，跳高 v²/2g = 0.459，余 9 毫米。但**画出来的廊面是 0.454**，所以按画的算余量只有 **5 毫米**。格子量化不影响这个余量：`heightAt` 是实时射线，不查格子；格子只决定落点开不开，而台面那一侧不收边，开到台沿为止。`climb.test` 在新 walker 上照过。但 5 毫米太薄。主创已同意：**迁移清单里记一条，#143 的判断留 2 厘米容差，不在旧数据上改。**

**7. 手机。** 会碰到他的几何其实不是 190 万面：竹、远山、天、雾、叶片按材质排除以后，**整个平面的建筑加树干是 73.4 万面**。在 Node 里对它建 BVH 用 **1.9 s**，约 **78 MB** 内存（位置、索引和 BVH 节点，`weigh.mjs`）。手机未验，按经验时间乘 3–5 倍，也就是 6–9 s，内存一样。三条办法：① 只对玩家所在的那一层台地建 BVH（首院 20.8 万面在 T4 上 0.8 s），换层时再建；② BVH 在构建时序列化随站点发出；③ 用简化的碰撞体。③ 就是第二份描述，又回到两份对不齐的老问题，不推荐。① 加 ② 不需要第二份描述。

**8. 维护。** three-mesh-bvh 0.9.18 的 `peerDependencies` 是 `three >= 0.159.0`（我们用 0.186）；它跟着 three 的版本发（最近一次 2026-11-03），API 只用 `MeshBVH`、`raycast`、`shapecast`、`closestPointToPoint`，都是多年不变的核心接口。升级 three 时卡住的风险低；万一卡住，格子在构建时已经烘好，运行时离开 BVH 只丢 `heightAt` 的射线（可以改成查格子）和镜头的射线。新旧并存开关的删除条件写在第九节。
