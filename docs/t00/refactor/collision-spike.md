# 走路、挡路、镜头遮挡从画出来的网格算：试验报告（#161）

> 状态：试验中，未定稿。数字在分支 `claude/collision-spike-161` 的提交上量，每节写明是哪个提交。T4 帧耗一节尚未量（见第八节）。
> 试验代码在 `tools/spike/`，只在分支上；`app/` 一行未改，`walk` 数据和现有测试一条未动。

## 结论先说

**推荐：换，但不是换成任何一个现成的「角色控制器」或「导航网格」库，而是用 three-mesh-bvh 做网格查询，自己烘一张 5 厘米的可走格子（做法照 Recast：地面高度、净空、台沿、按身体外廓收边、从入口洪水填充剔掉走不到的），在构建时烘好随站点发出，运行时只查表。** Recast 留作寻路的候选，不用它的可走面。理由：

1. 现在的五个已知 bug 里，三个在新做法下**不用写一行补丁就没了**（#148 台基四周、#154 点地走不出来、茶寮南端被圈住的那个点），第四个（#149 殿内柱）在新做法下**不可能发生**（画了柱就挡）；另外查出两个旧数据里没人报过的：**铜香炉根本没登记，他能直接穿过去**；枫树露出地面的根旧数据也让他踩进去。
2. 体积小：three-mesh-bvh gzip 后 **17 KB**（MIT）。Recast 224 KB，Rapier 1.1–1.6 MB，后两者都过了 issue 定的 300 KB 线或贴着线。
3. Node 里照样跑：同一份网格在 Node 里建 BVH 1.1–1.3 秒，烘格子 4.5–5.4 秒（只第一次，之后按三角形的哈希读缓存，11 毫秒）。现有单测原样跑在新 walker 上，用到 walker 的 19 个文件 142 条里，新 walker 用 0.38 圆柱时 **131 条直接通过**、用真实外廓时 129 条，没过的逐条有解释（第五节、附表），其中多数是断言写死了旧模型（「`r + BODY − 0.02` 处必须挡住」「台面正好 0.45」）。
4. 运行时便宜：`blocked` 查表 0.8–2 µs，`heightAt` 一条射线约 3 µs，`eyeShut` 4.0 µs（旧 2.2 µs）。

不推荐的两条现成路：

- **Rapier 角色控制器**：自己会爬台阶、贴墙滑、跳上矮台，手感是物理的；但 gzip 后 1.1 MB（拆分 wasm 版）到 1.6 MB（内嵌 wasm 版），每步 166 µs（含 `world.step`），要把「他」改成胶囊体并接管 `stride`、跳、落地，改动面最大，还解决不了镜头和寻路。
- **Recast 的可走面**：烘得快（同一份 20.8 万三角形 0.66 秒，比我们 JS 烘快七八倍），寻路 0.1–1 ms；但它**把台沿上下两侧都往里收一个身体半径**，茶寮、禅堂一米来宽的前廊和台基的侧边几乎收没（图 `recast-vs-grid.png` 红色），旧数据和新格子都让他站到台沿边上（跳下要求他离台沿 0.65 米以内）。这在 Recast 里不能单边配置。它也不剔走不到的面（殿内空壳整块算可走，图中蓝色），要自己按连通性剔。

所以迁移的形状是：**格子当可走面，BVH 当镜头和射线，寻路先沿用 `route.js`（它本来就是在格子上的 A*，只是格子来源换了），以后要更快再接 Recast 的 Detour 或在格子上做层次 A*。**

## 一、做了什么（验收 1）

`tools/spike/meshwalker.mjs` 的 `createMeshWalker` 与 `createWalker` 同形：`heightAt / blocked / onGround / floorAt / eyeShut`，以及 `eyeAt / landAt / onStairs / wall / railNear / setRoom / setLoft / room / loft`。数据只来自画出来的网格：`buildSite` 的 `site.root`、`trees.js` 的树、`props.js` 的香炉、`interior.js` 的房间、`ground.js` 位置上的一张平铺地面（Node 里没有画布，用同尺寸平面代）。试验区域外、上凌霄阁、进别的殿，它把问题交回旧 walker（`fallback`）。`yard.js` 的调用方式不变：`tools/spike/swap.mjs` 是一个 Node 加载钩子，把每一处 `import … from "app/src/site.js"` 换成 `site-swap.mjs`，其中只有 `createWalker` 换了；所以现有单测和 `tools/edges.mjs` 不改一字就跑在新 walker 上。

| 问题 | 怎么问网格 |
|---|---|
| `heightAt` | 从层的天花（首院取 3.0 米：高过大殿台基 1.5 米，低过最低的檐 3.54 米）往下一条射线，第一个朝上的面（法线 y > 0.5）就是地；标成「绕着走」的东西（蒲团、矮茶案）不算地，射线穿过去。 |
| `blocked` | 查烘好的格子（下面）。 |
| `floorAt` / `onGround` / `onStairs` | 地面射线停下那个面的材质：`paving` → 院子，带 wood → 木，`steps` → 台阶（`path`），其余 → 石。 |
| `eyeShut` | 离任何面 12 厘米内；或者脚下是走不到的格子（殿身、墙身、台基身），且眼在那一处最高的面以下；或者四面和头上都被围住。 |
| `railNear` | 一个球内有不朝上的面（地面不算），且在头高以下。 |
| `wall` | 15 厘米内有东西，或在封闭实体内（向 +x 的射线先碰到背面）。 |

**烘格子**（`bake`，照 Recast 的做法，但在 JS 里、对我们的规矩做了两处不同）：

1. 每格地面高度：上面的射线。
2. 每格是不是「边界」：格子半径内有东西，高度在地面上 `CLIMB`（0.25 米，比任何一级踏步 0.10–0.17 高，比最矮的台基 0.30 低）到 `CLEAR`（1.45 米）之间；标成「绕着走」的东西从地面起就算。
3. 台沿：邻格地面比本格高出 `CLIMB` 以上，本格（台下那格）是边界。**台面那一侧不算边界**，所以他能站到前廊最边上，和旧数据一样（Recast 两侧都收，这是不同之一）。
4. 收边：每个边界格按**他在那个高度上的外廓半径**把周围的格子关掉。外廓不是一根粗 0.38 米的圆柱，而是 `tools/edges.mjs` 的 `outline()` 从两个身体模型、六种姿势量出来的每 5 厘米高度的最大伸出（`tools/spike/outline.json`：脚边 0.34，腰下袖口 0.38，胸口以上 0.14–0.20）。边界只关掉它高过脚面的格子：台基侧面不挡站在台面上的人（不同之二）。
5. 洪水填充：从院子中央（殿内从门内一步）出发，八向、地面差不超过 `CLIMB`，填不到的格子也关掉（殿身空壳、桌面、栏杆顶）。

`SPIKE_BODY=cylinder` 把外廓换回旧数据的「处处 0.38」，用来把「身体用什么形状」和「几何从哪来」两件事分开看。

## 三、他的宽度（验收 3）

- 新做法里「他」是 `edges.mjs` 量出来的那个旋转体，不再是一根 0.38 米的圆柱：烘格子时，每个挡路的东西按它所在的高度取他在那个高度的伸出。所以**旧数据用一个数、`edges` 用一条曲线的那种两份对不齐，在这里是同一条曲线**。
- 用外廓比用圆柱多出能走的地方 17.8 m²，主要是胸口高度的东西（禅堂前廊的格扇、柱身中段）：他在那个高度只伸出 0.14–0.20 米。
- `pnpm run edges` 换新 walker 跑：见下面「edges」一行（后台在跑，完成后补上）。edges 用的是同一条外廓，所以新做法的结论应当与 edges 一致；格子化带来的误差在一个格子的对角线一半以内（3.5 厘米），`edges.test.mjs` 里禅堂后角柱那一条差的 1 厘米就是它。

## 五、镜头（验收 5）

`eaves`、`sweeps`、`follow`、`director` 四组单测原样跑在新 walker 上（提交 73cb183，外廓与圆柱结果相同）：**27 条过 24 条**。

- `eaves`、`sweeps` 全过（观音殿、各殿檐下、台沿跳下落点）。
- `follow`「绕首院一圈镜头不跳」：一帧里眼的高度自己变了 0.06 米，在 (−10.8, 7.9)。原因是 `eyeAt` 我用的是周围五点地面平均，碰上了树下土堆和台沿；旧的 `eyeAt` 只在台阶上取斜坡。要另做一个「沿走过的路平滑」的 `eyeAt`，不是网格的问题。
- `follow`「沿中轴到大殿台阶」：测试写的路线穿过 (0, 14.19)，离香炉中心 1.19 米；**旧数据没有香炉，这条路线本身就穿过香炉的炉沿**。路线要绕开香炉。
- `director`「茶 从 30° 转过去」：找不到绕他的镜头路线。新的 `railNear` 把茶桌、凳子、树都算作「要离开 12 厘米」，比旧的（只算栏杆）严，绕路时可走的点不够。要么 `railNear` 只认标成栏杆的东西，要么转场的搜索放宽；这是要定的口径。

另在首院按 25 厘米、离地七个高度共 28.6 万点比了 `eyeShut`（`eye.json`）：

| 离地 | 都关 | 都开 | 只旧关 | 只新关 |
|---|---|---|---|---|
| 0.4 m | 16092 | 22577 | 1823 | 340 |
| 1.8 m | 11967 | 24426 | 4126 | 313 |
| 3.6 m | 11068 | 24080 | 5091 | 593 |
| 7.0 m | 10239 | 23357 | 7008 | 228 |

「只旧关」最多的几类：旧数据把**整座殿的 `solids`（含台基侧面、背面）上方 5.5 米**都关了，而新做法里台基侧面已经能走，眼也就能在那里；**檐下梁架、瓦之间的空隙**（旧数据按 `walk.roofs` 从梁底到屋脊整块关掉，新做法只看离面 12 厘米）。后者是新做法真的放松了的地方：要么保留由 `building.js` 参数算出来的 `walk.roofs`（它不是手对的，是生成的），要么对每个屋顶取凸包。**建议保留 `roofs`。**

## 六、寻路（验收 6）

- **`route.js` 原样用新 walker**：`route.test` 全过，包括「从每个前廊两端、茶案和蒲团旁，到院子的 234 条路线」和「所有者报的那个点（茶寮南端 −12.85, 5.98）走出来」——后者的前提「这个点是挡着的」在新做法下不成立了：**这个点本来就不该挡**，#154 的根因在新做法下没有。
- **Recast**（`recast.json`）：同一份三角形，cs 5 厘米，烘 0.66 秒，397 个多边形；寻路四条（茶寮南端到院子、院子到大殿前廊、茶寮到禅堂、院子到大殿台基侧面）各 0.08–1.0 ms；站点查询 1.3 µs。缺点见「结论」：两侧收边、不剔不连通的面。
- **能不能把 `route.js` 和 `director.wayRound` 合成一份**：能，而且新做法让这件事更自然。两者都是「在一张格子上 A* 再拉直」，差别只在格子的来源（前者问 `blocked`，后者问 `inWay`）和高度（前者在脚下，后者在眼的高度）。烘好的格子给前者；后者的「眼能不能在这」本来就要对网格打射线。合成后是一个 `gridSearch(open(i, j), cost, budget)` 的生成器，两边各传自己的 `open`。这一步不依赖换不换网格，可以先做。

## 七、Node 里（验收 7）

| | 时长 |
|---|---|
| 整套单测（旧 walker，361 条） | 44.3 s |
| 用到 walker 的 19 个文件，旧 walker | 28.6 s |
| 同上，新 walker，第一次（每个进程自己烘） | 45.6 s |
| 同上，新 walker，缓存在 | 38–41 s |
| 每个进程：收集三角形 + 建 BVH | 1.1–1.3 s |
| 每个进程：烘格子（首院 + 殿内，121 万格） | 4.5–5.4 s；有缓存 11 ms |

- three-mesh-bvh 是纯 JS，Node 里直接 `import`；Recast、Rapier 的 WASM 在 Node 里 `await init()` 分别 40 ms、211 ms，也都能跑。
- 慢的是**收集三角形**（逐个三角形算世界坐标、判区域）和**烘格子**的两遍射线。前者可以换成直接用 `mergeStatic` 合好的几何（已经在世界坐标里），后者在构建时做一次、按三角形哈希缓存（试验里已经这样做），或者交给 Recast 的体素化（快七八倍）只取它的高度场，自己收边。全场（不只试验区）121 万格 × 约 3.6 倍面积，按现在的写法冷烘约 18 秒——**必须是构建时的产物，不能在每个单测进程里现烘**。

## 八、性能（验收 8）

- **包体积**（`sizes.json`，同一个 Vite 打包最小用法，gzip −9）：three-mesh-bvh **17 KB**；recast-navigation 224 KB（其中 wasm 215 KB）；Rapier 内嵌 wasm 版 1607 KB，拆分 wasm 版 wasm 本身 1141 KB。
- **烘好的格子**：首院 + 殿内 121 万格，每格 4 字节高度 + 2 字节原因 + 1 字节开关 = 8.5 MB 原始；格子大多是平的，gzip 后估计在一两百 KB（未量）。全场按 10 厘米烘约 1/4。
- **每次查询**（Node，本机 CPU）：`blocked` 0.8–2.1 µs（旧：查矩形和圆，约同量级），`heightAt` 约 3 µs，`eyeShut` 4.0 µs（旧 2.2 µs）。一帧里 `stride`、`follow`、`pickFloor` 加起来调用几十到两三百次，量级在 1 ms 以内，与 GPU 无关。
- **T4**：**尚未量。** 要量就得把新 walker 接进页面（`?walker=mesh`，在 `mergeStatic` 之后收集网格、读构建时烘好的格子）。所有者批的 30 分钟还没动。下一步：先在本地 SwiftShader 跑通「同一页新旧交替各三次」的脚本，再上 T4 一次量完（首院高档 1080p、低档手机尺寸，载入多出的毫秒数，`report.json` 带 site 指纹）。

## 九、迁移方案（验收 9）

每一步 main 全绿，每一步都可单独回退。估计 **6 个 PR**。

1. **合并两个寻路**（不依赖网格）：`route.js` 与 `director.wayRound` 共用一个格子 A* 生成器。删掉一份搜索代码。
2. **构建时烘格子**：`tools/bake-walk.mjs` 在 Node 里建场景、建 BVH、烘格子，写 `app/shared/walk/<level>.bin`（随 `KEPT` 拷进 `dist/`），按三角形哈希命名；`pnpm build` 和单测在哈希不符时重烘。加单测：格子与当前几何同哈希。页面和单测都只读文件。此时还不用它。
3. **新 walker 上线于首院**，旧 walker 作回退（与本试验的 `fallback` 一样），`?walker=old` 可切回。在画的地方补上意图标记：蒲团、矮茶案、香台挂 `userData.walk = "post"`；门挂 `userData.door = hallId`（`blocked` 在门线挡住，与现在一样由门的触发器进殿）。改掉写死旧模型的断言（`r + BODY − 0.02` 改成「`edges.outline` 在那个高度的伸出」，台面 0.45 改成「与画出来的台面同高」）。修香炉。#148 的台基绕行、#154 的点地在这一步自然得到。
4. **全场**：其余两层台地、山路、凌霄阁的回廊（多层：格子按层存，`setLoft` 选层）、八间殿内。删 `walk.solids / decks / ramps / posts`，删 `createWalker` 里对应的 150 行。`walk.drops` 改由格子派生。
5. **镜头**：`eyeShut` 改为 BVH 射线 + 格子；`railNear` 定口径；`eyeAt` 改为沿路平滑。`walk.roofs` 保留（它由 `building.js` 参数生成，不是手对的），雪的遮蔽 `shelter.js` 照旧用它。
6. **工具和测试**：`edges.mjs` 的「先洪水再量身体」变成「读格子再量身体」（同一份外廓），大约减半；`edge-coverage.md` 的表照出。`sweeps`、`nearplane`、`standing` 改成对 BVH 打射线（`eaves.test` 已经这么做，只是对一座殿）。

**仍要手写的**（都是意图，不是几何）：这是一扇能进的门（`site.halls` 的 `door/out/outYaw`）；这是一个座位（`site.seats`）；这是一件绕着走、不许踩的东西（`userData.walk = "post"`）；这是一处要点的地方（`site.places`）；层与入口（格子洪水的种子、凌霄阁的层）；`walk.roofs`（生成的，保留）；`shade`（地面阴影，生成的，保留）。
**可以删的**：`walk.solids / decks / ramps / posts`（约 277 个柱、61 块实体、31 块台面、16 段台阶）、`walk.rails`、手写的 `walk.drops`；`createWalker` 的大部分；`edges.mjs` 里为守 `walk` 数据而有的「每个零件归哪座殿」那部分可以保留做报告，但不再是守门。
