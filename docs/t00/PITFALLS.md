# T00 踩过的坑：从上线到 0.6.0

复盘日期：2026-11-20。所有者的要求：「查看全部 git log，总结 T00 从上线到现在 0.6.0 版本踩过的坑，总结一下后续关卡开发流程」。流程在 [`../LEVEL-PLAYBOOK.md`](../LEVEL-PLAYBOOK.md)，这一页是它的依据。

## 怎么读这一页

- **看了什么。** `origin/main` 到 `98057f4` 的全部 422 个提交（2026-11-11 至 11-20，`v0.1.1` 到 `v0.6.0` 六个标签）；标题以 fix 开头的提交 94 个，逐个读了提交说明的前几行；GitHub 上 127 条 issue 的标题、标签、开关时间，其中约 60 条读了背景一节；`AGENTS.md` 的三次每晚复盘、`LESSONS.md`、`docs/handoff/`、`docs/t00/decisions.md`。
- **没看什么。** 没有逐个读 PR 的评论和评审对话，也没有读各会话的记录；`docs/HANDOFF.md`（19 万字）只按关键词查。所以「怎么发现的」以提交说明和 issue 背景里写的为准，那里没写的标「未核」。
- **没有一个提交是 `git revert`。** 历史里撤回都是用新提交改回去的（例如 #241 把 #207 换的字体换回、`2a95580` 把雕刻身体改为默认关）。下面把这类也算作撤回。
- **时间一律换成 UTC**（仓库里的作者时间混着 +0800 和 −0800 两种时区，直接读日期会差一天）。「隔了多久」是引入提交到修复提交的间隔。
- **代价是估的**：数的是为这件事合进 main 的 PR 或提交，写「约」；没有算会话时长和额度。
- **「推断」** 标在没有提交或 issue 直接写明、由本页作者连起来的地方。
- 每条的六项：现象、根因、引入与修复、怎么发现、代价、现在的防线。没有防线的写「无」，并在文末的缺口清单里给建议。

## 一、碰撞与可走

<a id="a1"></a>
### A1 同一个世界描述了两遍：画的是一份，走的是另一份手写矩形

- **现象**：台基四周看着有空地走不过去（#148）；矮台跳不上（#143）；蒲团坐不了（#144）；点地只走直线、被台沿挡住就不动（#154）；身体进柱子、栏杆、桌子 66 处（#16）；禅堂门内的坐榻画的是整条、数据里留了过道，他一直从坐榻里穿过去（`LEVEL-PLAYBOOK.md` 附录甲）。
- **根因**：能走的地、挡路的东西、台沿、镜头遮挡另写在 `walk.solids/decks/ramps/posts/drops/rails/roofs` 里，靠人和画出来的几何对齐。
- **引入与修复**：手写矩形从四进院落那版就有（`7074e8a`，11-12），台阶改成踏面、亭柱挡路是 `d98a2bd`（11-14）。逐处补：`91a6343`（11-15）、#67、#121、#151、#155、#157。换做法：#196、#198（11-18，烘焙）、#266（11-19，首院）、#276（11-19 19:14，全图）、#305、#321（11-20）；镜头是 #354。从引入到全图换掉约 7 天。**第 6 步（删掉手写数据和 `?walker=old`）还没做**，镜头的 `railNear`、`wall`、`landAt` 和脚步的 `floorAt` 仍问手写数据（`CLAUDE.md`）。
- **怎么发现**：独立评审（#16 的 EDGE-001、EDGE-002）；所有者手机实测（#143、#144、#148、#154）；主创 11-17 自审 147 个提交后归成一个根（`AGENTS.md`「先找轮子，再动手」：35 个修复里约四成）。
- **代价**：约 20 个 PR（11-17 前的约 14 个是主创自审的估数，之后迁移 7 个按提交数；含 A2、A4、A7 里列的）。全场最大的一项。
- **防线**：`tools/bake-walk.mjs` 加 `walk-diff`（CI 每个 PR 都跑，命名地点走不到就失败）；`gridwalker.test`；`pnpm run edges:grid`、`nearplane:grid`；规矩「世界只描述一遍」「同一处修到第三次换做法」。手写数据没删之前，画一样东西仍要在两处写（`CLAUDE.md`「while it is kept…a thing drawn must still be written there」），这一半**无**防线。

## 二、镜头

### B1 跟随的镜头一帧跳六米，朋友玩晕了

- **现象**：柱子或钟鼓楼挡在中间时，镜头一帧里跳 6 米；台沿处升降 0.67 米；镜头进了观音殿的窗棂和屋檐；站在台地挡土墙下，镜头升高 7 米，人掉出画面。

## 三、构建与部署

<a id="c1"></a>
### C1 软件渲染里一切正常的着色器，在真显卡上半屏变黑，上了线

- **现象**：从山门往香炉看，殿门和香炉入画就偶发半屏黑。
- **根因**：烟的片元着色器 `pow` 的底数在线头处略小于零，真显卡返回 NaN，再被泛光抹成一大片；软件渲染复现不出。
- **引入与修复**：#231（11-18 19:43）→ #236（21:46），约 2 小时；#237（22:14）加守卫。
- **怎么发现**：所有者在正式站上（`AGENTS.md` 2026-11-19 复盘）。
- **代价**：2 个 PR，一次线上事故。
- **防线**：`pnpm run check` 扫全场着色器的 `pow`、`normalize`（#237）；规矩「改着色器的 PR 合并前在真显卡上看过」；canary（C2）。守卫只认它知道的几种写法，「改了着色器却没有 T4 报告就不能合」**无**自动检查。

<a id="c2"></a>
### C2 main 一合并，几分钟后玩家就玩到

- **现象**：#291 带进的镜头点头，合并几分钟后玩家就遇到；NaN 黑屏同理。
- **根因**：推到 main 过了三个检查就上生产；台阶、跳下的场景与部署同时跑，不拦部署（#308 的背景）。
- **引入与修复**：从第一次部署（`c1f39d3`，11-12）到 #309（11-20 00:38），约 8 天。0.6.0 第一次走标签上生产时，线上比对被验证页挡住误报，#345 修。
- **怎么发现**：所有者定的流程（#308）。
- **代价**：2 个 PR，加上它放大的两次线上问题。
- **防线**：main 只上 canary，版本标签才上生产；`quick`（`stairs`、`drop`）挡在部署前；`deploy-tag.yml` 一键回滚；上线后按哈希读回。

<a id="c4"></a>
### C4 测试用的服务器和线上的不是一回事

- **现象**：界面样式表搬家后 main 的 `boot` 红（.css 被当成二进制，#29）；发布的页面没有 `<!doctype html>` 和 viewport，手机把它画成 980 像素宽（`CLAUDE.md`）；加了 `/api` 以后，烘门洞的文件服务器回 404，main 的 `site` 任务失败（#358），e2e 的服务器同样（#355）。

## 八、多会话协作与合并冲突

<a id="h1"></a>
### H1 两个会话共用一处，互相覆盖

- 存储桶：见 C6（#128）。
- 并入 main 时丢了别人的一行（#205 丢了 `#community` 的版面规则，主创读差异时看到）。**防线**：规矩「并入 main 后逐行过一遍只应有新增的文件」，无工具。
- 两份只增不改的文档（`HANDOFF.md`、`SOURCES.md`）反复冲突 → `.gitattributes` 的 `merge=union`（`9c09ae5`，11-17）。
- 新关卡的同类风险：`docs/t05/PLAN.md` 自己写了 S1 动 `site.js` 全文要排在别的 PR 之后。

<a id="h2"></a>
### H2 合早了

- **现象**：#178 合早了三分钟，3D 评审的「先别合」已在消息队列里；#133 在重测跑完前合入；#23 在 CI 还在跑时应所有者要求合入。
- **防线**：规矩「合并前清空消息队列，重读 head 和最新评论」「有评审方盯着的 PR，评审方说过才合」「只合评审过的那个提交（`expectedHeadSha`）」。

<a id="h3"></a>
### H3 同一件事开了两条 issue

- **现象**：#75 和 #272 是同一处垂带缝；#294 之前已有 #148、#154 相近。
- **防线**：规矩「接新任务先查已有 issue；每晚复盘时清 issue」。

<a id="h4"></a>
### H4 一个 PR 里混进别的东西

- **现象**：#132 的差异里混进删除旧证据；#269 把七份 T4 报告约 1.9 万行 JSON 放进 git，合并前移出。
- **防线**：规矩「一个 PR 只做一件事，推之前对着目标看一遍文件清单」；`evidence check` 拦 1 MB 以上的文件，拦不住大段文本。

<a id="h5"></a>
### H5 派工和计划对不上

- **现象**：决定重构树之后，主创仍让主开发在旧 `trees.js` 上修接缝，所有者指出才停；镜头偏左（#271）挂着没派，所有者对用户说已修。
- **防线**：规矩「派工前对一遍因重构暂缓的清单」「反馈里没修的，明说没修」。

<a id="h6"></a>
### H6 会话又长又贵，停了没人知道

- **现象**：#156 一个小改动跑了近四小时没开 PR（时间花在软件渲染下整套重拍三次）；#87 的对话用到 87 万 token；三个常驻评审合计约 450 美元；用量限额一天停两次，停的时候没推的活只在那台机器里。
- **防线**：规矩「先推代码，后拍图」「调的时候看一帧，定了才拍一套」「一个 issue 一个对话」「过二十万 token 写交接换新」；T4 放开用。

## 九、需求理解

<a id="i1"></a>
### I1 所有者指着一张图，主创理解成了另一件事

- **现象**：「喫茶去那块匾轻重不匀」被理解成字体笔画不匀，把全场匾换成印刷体（#207）；所有者指的是匾前的黑块（斗拱挡着，#216 已修）。#241 把字体换回。
- **引入与修复**：#207（11-18 11:14）→ #241（23:42），12.5 小时。
- **代价**：3 个 PR（#207、#241、#242），外加按字补墨的工具作废。
- 同类：茶寮台基跳不下来，主创先说是回归，实测新旧一样，所有者再试才知道是**西面**；#266 预览的穿模先当近裁剪面查，所有者说的是「跑到了地板下面」。
- **防线**：规矩（`AGENTS.md`「听清所有者指的是什么」：用他给的地址、真实输入复现，结论写成固定格式）。issue 模板的背景一节要原话照录。

<a id="i2"></a>
### I2 音量靠猜，改了三次

- **现象**：脚步声先加 6 dB（#53），再降 10 dB（#65），再降 10 dB（#98）。
- **根因**：没有先和所有者定参照。#65 才去量了《小王子》的发布文件，所有者听了三档对比；#98 是所有者说「若隐若现」。
- **间隔**：11-16 00:43 → 13:15，12.5 小时，三个 PR。
- 同类：山声偏大、殿内外一样（#331 → #334）；竹林的风（#69）。
- **防线**：`steps.test`、`mountain-air.test` 守定下来的电平；`tools/music.mjs`、`tools/mountain-sound.mjs` 出试听文件。「定电平之前先出三档给所有者听」写进了新流程的声音阶段。

<a id="i3"></a>
### I3 验收标准本身不成立，或和目标相背

- **现象**：#270「下台阶后膝更直」腿长所限做不到，撤回；#192 的「墨占字框相差 15%」照着做反而更不匀；#296 写「只改文档不跑单测」，违背 #187 当初特意留单测的决定。
- **防线**：规矩「验收标准写之前想清几何和物理上成不成立」「写 issue 前看已有的决定」「量法先于阈值」。

<a id="i4"></a>
### I4 主创的判断没核就说出口

- **现象**：推荐 T05 时只读了五份决定记录就说「基本复用」「范围最小」，子任务核全文后两条不成立；#129 没在手机上拖一下菜单就说「真问题」；参考「magpie」查成了 Apache Magpie。
- **防线**：规矩「说出口的判断先核到能下的程度，核不到就写未核；方向性的推荐先派一次独立核实」。
