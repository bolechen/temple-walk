# 关卡手册：一关从调研到发版

所有者 2026-11-17：「T00 的工作哪些是可以复用的，要不要整理成后续关卡的工作流」；2026-11-20：「总结 T00 从上线到现在 0.6.0 版本踩过的坑，总结一下后续关卡开发流程」。

这一页是 2026-11-20 的改写。原来的手册只记 T00 实际走过的顺序；这一版把它排成**九个阶段，每个阶段有进入条件和退出条件**，依据是 [`docs/t00/PITFALLS.md`](t00/PITFALLS.md)（T00 从 11-11 到 0.6.0 的 422 个提交里踩过的坑，下文用它的编号，如 A1、F2）。

**这一页的地位。** 阶段和关口是从 T00 的教训里**归纳出来的建议**，T00 自己没有按这个顺序走过（它是做完才评审的，见 PITFALLS 第十节第 4 条）。它没有在任何一关上验过；T05 走完第一阶段后按实际修订。凡是写「所有者拍板」的地方，这一页只说要问什么，不替所有者定。

原手册的内容搬到了哪里：「二之二 走路数据」在附录甲，原样保留；「三 新开一关要建的文件」在附录乙；「五 地面的记忆」在附录丙；「四 T00 的教训」并进了各阶段的「T00 的坑」和 PITFALLS；「每条线收尾请所有者走十分钟」（原 §四）现在是每个阶段退出条件里的一条。

## 一、每关重做的，和拿来就用的

| 每关重做（内容） | 拿来就用（引擎与工具） |
|---|---|
| 实地与文献调研，「灵魂元素」和「有意没有做的」清单 | 建筑、台阶的生成器；从画出来的网格烘可走地面 |
| 平面：建筑、台地、路径、可去的地方 | 小沙弥：骨骼、行走、坐、两种视角、跟拍、打卡镜头 |
| 验收机位、美术目标图 | 材质、四季四时、雾、阴影、画质分档、调色 |
| 仪式与朱印（每关几枚、做什么，由该关 PRD 定）、每处的机位 | 全合成的配乐引擎、钟、脚步、环境声 |
| 匾额书法、殿内陈设与悬挂的真迹 | 纸上墨的界面、设置、留影、朱印帐、四种语言、鸣谢 |
| 每个效果的出处（`SOURCES.md`）、素材授权登记 | 单测、`edges`、`nearplane`、`walk-diff`、`mobile-audit`、T4 测帧与指纹、出图与录像工具、证据库 |

右栏有多少真的「拿来就用」，以 [`docs/t05/LEVEL-SPLIT.md`](t05/LEVEL-SPLIT.md) 为准：2026-11-20 引擎里还有九处直接读 T00 的数据，S1 已合（#364），S2 起在做。**一个工具或测试还不认 `--level` 时，它守不住新关卡**；下面每个阶段的「必须跑」里，凡是带 `--level` 的，都以 `LEVEL-SPLIT.md` 的对应步骤合并为前提。

## 二、九个阶段

每个阶段五样：进入条件、产出、必须跑的、所有者拍板的、退出条件；最后是 T00 在这里踩过的坑。**退出条件全部满足，并且在同一个提交上有证据，才进下一阶段**（`CLAUDE.md`：没有那个提交上的运行证据，不标通过）。阶段可以并行准备（例如白盒期间写声音的方案），但后一阶段的东西不在前一阶段的关口过之前合进 main。

通用的规矩不在每个阶段重复，都在 `AGENTS.md`：先查现成的做法；一个 issue 一个 PR 一件事；先推代码后拍图；交活写明在哪个提交上跑了什么；改着色器的在真显卡上看过；看得见的改动主创合并前自己到预览里站到玩家的位置看。

### 阶段 1　调研

- **进入条件**：所有者点了下一关是哪座寺。
- **产出**：`docs/<关>/` 的调研包：这座寺凭什么值得走（灵魂元素，一条一个出处）、有意不做的、实地尺寸与它们的出处、文化与礼仪上的分寸、可用素材的来源和授权。
- **必须跑**：无代码。每条出处标核到哪一步（读了原文、转引、照片、按常理、自拟），和 `SOURCES.md` 的写法一样。
- **所有者拍板**：做哪座寺；灵魂元素和有意不做的清单；要不要请顾问。
- **退出条件**：
  1. 调研包合进 main；每个灵魂元素有出处，没有出处的标「提案」。
  2. 「有意不做的」至少列了宗教分寸上不做的事。
  3. 方向性的结论（例如「引擎基本复用」「范围最小」）经过一次**不是主创自己**的核实，核实的结果写在包里。
- **T00 的坑**：[I4](t00/PITFALLS.md#i4)（主创只读了五份记录就推荐 T05，两条不成立）；[F6](t00/PITFALLS.md#f6)（素材先用上，授权后核）。

### 阶段 2　PRD

- **进入条件**：阶段 1 退出。
- **产出**：`docs/<关>/PRD.md`：范围（几区）、走线与站点、锁定机位的草案、基线季时、仪式与朱印、与上一关的衔接、声音的方向、**每条都可判定的验收标准**、待所有者定的清单（每项带选项、推荐和理由）；`PLAN.md`：分阶段和第一阶段的 PR 清单；`docs/<关>/asset-register.csv` 和 `SOURCES.md` 的空表建好。
- **必须跑**：`pnpm run check`、`node tools/evidence.mjs check`。开工前查过的现成做法写进 PRD（`AGENTS.md` 铁律）。
- **所有者拍板**：PRD 里「待所有者定」的每一项（范围档位、印数、基线季时、寺名、花钱的事）。**没答的项，依赖它的 PR 不开工。**
- **退出条件**：
  1. PRD 合进 main，待定清单每项写着所有者的原话和日期。
  2. 每条验收标准写了「怎么判」：一条命令、一个测试名、一个数，或一组命名机位。写之前想过几何和物理上成不成立。
  3. PRD 里用到的工具，哪些今天还不认新关卡，列成表并排进计划（否则那条验收判不了）。
  4. 引擎要先改的（关卡抽离、缺的建筑式样）排在第一个内容 PR 之前。
- **T00 的坑**：[I3](t00/PITFALLS.md#i3)（验收标准做不到，或和目标相背）；[I1](t00/PITFALLS.md#i1)（读错所有者指的是什么）；T00 的验收范围和美术目标是 11-14、11-16 才写的，建筑已经在了（`docs/t00/art-goal.md`、#73）。

### 阶段 3　白盒可走

先用体块走通全程，再谈好看。

- **进入条件**：阶段 2 退出；关卡能按名字装进引擎（`?level=<关>`），能烘自己的地面。
- **产出**：`app/levels/<关>/`：地形、台基、踏道、每座建筑的外壳、命名地点、到达点、锁定机位；烘出的地面；`docs/<关>/camera-manifest.json`；一组白盒图。走路数据照附录甲，不手写 `walk.*`。
- **必须跑**（都在交活那个提交上）：
  - `pnpm run verify`；`pnpm run test:grid`；
  - 新关卡的洪水填充单测（每个命名地点、座位、殿门、机位都从到达点走得到）；
  - `node tools/bake-walk.mjs` 与 `node tools/walk-diff.mjs … --png=`，**第一次烘出来的整张可走图由主创看过一遍**（新关卡没有基准，`walk-diff` 报不出「多了什么」）；
  - `pnpm run edges:grid`、`pnpm run nearplane:grid`（带关卡名）；
  - e2e：新关卡的 `walk` 场景，真实按键、正常步速走一遍全程，另有 `?fast=1` 的一遍；
  - **向外看一圈**：`horizon.test` 对新关卡跑，或在它认关卡之前，从每个命名地点用 `shots.js` 朝四个方向各出一张（地平线以下不露天，远处有东西可看）；
  - **上一关不变**：T00 的六个机位和十六个殿内机位像素不变、`t00.bin` 的指纹不变（改到引擎或 `building.js` 的 PR 才需要）；
  - T4：同一个 Job 里上一关的基准机位与新关卡的机位交替量 `__cost`。
- **评审**：建筑外壳的正、侧、俯三向图给建筑结构评审，**在加任何细部之前**；改 `building.js` 的单独一个 PR。
- **所有者拍板**：走线的长短和节奏（走一遍说够不够）；白盒阶段的关卡让不让玩家进得去（见第四节缺口 6）。
- **退出条件**：
  1. 上面每一项在同一个提交上绿，命令和提交写在阶段的交付记录里。
  2. 结构评审对每座建筑的柱网、开间、屋顶式样和台基高度书面说「可以往下做」，偏差记进 `SOURCES.md` 与决定记录。
  3. 向外看一圈没有露天和硬切口；有的话开了 issue 并排了期。
  4. 所有者用自己的手机按一张不超过十项的清单走过十分钟，结论记进交付记录；没走的写「未经真机」，不算退出。
  5. 手机低档量过一次帧耗（`tools/device.cjs`），数记下来，先不设线。
- **T00 的坑**：[A1](t00/PITFALLS.md#a1)、[A2](t00/PITFALLS.md#a2)、[A3](t00/PITFALLS.md#a3)、[A4](t00/PITFALLS.md#a4)（世界描述两遍、他有宽度、只在加速时过得去的门、画了没登记）；[F1](t00/PITFALLS.md#f1)、[F2](t00/PITFALLS.md#f2)（景观和结构评审放在做完之后）；[D2](t00/PITFALLS.md#d2)（测试里写死坐标）；[E2](t00/PITFALLS.md#e2)、[E3](t00/PITFALLS.md#e3)（跨 Job 比数、没有手机的数）。

### 阶段 4　灰盒

体块换成有正确构造的形体：柱、梁、斗栱、屋面、栏杆、陈设的中模；材质先用引擎已有的。

- **进入条件**：阶段 3 退出。
- **产出**：建筑与陈设的形体；殿内的柱网、梁架；每类东西的出处行；`docs/<关>/around-review.md`。
- **必须跑**：
  - 阶段 3 的全部（形体一改，可走面就变：`walk-diff` 每个 PR 都看，**每座建筑多出来的可走面积超过 1 m² 的，PR 里说一句，并从那块地朝外、朝墙顶、朝背面各看一眼**）；
  - 绕一圈普查：`node tools/around.mjs`、`tools/around-gpu.sh`、`tools/around-sheet.py`，发现逐条开 issue；`lettered-faces.test` 一类守「带字带画的只画在一个朝向上」的测试对新关卡跑；
  - 改形体的 PR：改前改后各一套正、侧、俯；
  - 镜头：`follow.test`、`spring-arm.test`、`sweeps.test`、`eaves.test` 在新关卡的路线上跑（最窄处、最长的台阶、最高的室内各一条）；
  - T4：三角形和绘制次数对预算（`__census()`），超了先停下报告。
- **评审**：建筑结构评审逐座复核；3D 模型评审看陈设和树。
- **所有者拍板**：凡是「为了能站人、能看见」偏离史实的地方；预算超了砍什么。
- **退出条件**：
  1. 普查的每条发现要么修了，要么有 issue 并写明不挡下一阶段的理由。
  2. 结构评审的 blocker 和 major 清零。
  3. 每个命名地点四周和每块新放开的地上，`edges:grid` 0 处超限，`nearplane:grid` 0 处切割。
  4. 帧耗在 PRD 的预算内（T4，同一个 Job 的差值）；手机再量一次。
  5. 所有者再走十分钟。
- **T00 的坑**：[F3](t00/PITFALLS.md#f3)、[A5](t00/PITFALLS.md#a5)（只做了一面；放开新地方露出背面）；[F2](t00/PITFALLS.md#f2)（结构四个阶段）；[B1](t00/PITFALLS.md#b1)（镜头进屋檐、一帧跳六米）；[E1](t00/PITFALLS.md#e1)（屋顶是三角形的大头）；[F4](t00/PITFALLS.md#f4)（有机的形体不要手写生成器，先找现成的）。

### 阶段 5　美术

- **进入条件**：阶段 4 退出；每个代表性机位有一张目标图和可量的指标（`tools/look.py`），目标之间不打架（T00 的 A2 与 A3 抢太阳方向，改的是目标的季时，不扭光）。
- **产出**：材质、光、雾、调色、植被、造像与彩画；每件进产物的素材在登记表里的一行；鸣谢页的条目。
- **必须跑**：
  - `shots.js` 出锁定机位，对目标图量指标；先做便宜的（调色、雾、软阴影），量过再上贵的；
  - **改着色器的 PR 合并前在 T4 或所有者的 Mac 上看过**，运行号和站点指纹写进 PR；`pnpm run check`（含着色器守卫）；
  - 加几何或渲染通道的：T4 前后各量一次；手机低档量一次；`?tour=` 看最长的一帧；
  - 生成或外来的模型：`asset-register.test`、`notices.test`、`fonts.test`；人物类的在站、走、上台阶、坐几个姿势下从四面看（`tools/novice-views.cjs` 一类）；
  - 素材的授权**在用进产物之前**核，按收费上架的口径。
- **评审**：独立评审在新证据上给结论；3D 模型评审；景观评审（远景）。
- **所有者拍板**：目标图；花钱的事（Tripo、付费素材）；生成的模型够不够庄严；任何涉及宗教形象的取舍。
- **退出条件**：

  2. 登记表里没有「未核」的行；鸣谢页齐。
  3. 帧耗仍在预算内；真显卡上从每个命名地点转一圈没有黑块（#238 的做法）。
  4. 所有者走十分钟。
- **T00 的坑**：[C1](t00/PITFALLS.md#c1)（着色器 NaN 上线）；[F5](t00/PITFALLS.md#f5)（雕刻身体上线一小时就关）；[F6](t00/PITFALLS.md#f6)（授权后核）；[F7](t00/PITFALLS.md#f7)（证据图只拍了想到的角度）；[F8](t00/PITFALLS.md#f8)（从殿外看殿内三轮）；[E4](t00/PITFALLS.md#e4)（第一次画时卡顿）；[B3](t00/PITFALLS.md#b3)（说不清的像素先问 `__pick`）。

  4. 所有者在手机上从头走到得印。
  5. PRD 要求的外部意见（T05 是礼仪顾问）拿到并逐条处理。
- **T00 的坑**：[B4](t00/PITFALLS.md#b4)（屏幕元素压在脸上）；[B6](t00/PITFALLS.md#b6)（收尾遇上息屏）；[A6](t00/PITFALLS.md#a6)、[G6](t00/PITFALLS.md#g6)（修法没覆盖所有入口，殿里接不回去）；[G1](t00/PITFALLS.md#g1)、[G2](t00/PITFALLS.md#g2)、[G3](t00/PITFALLS.md#g3)（菜单越加越长、四种语言撑破版面、触屏没有跳）；[D4](t00/PITFALLS.md#d4)（新功能改了老场景的前提）；[F7](t00/PITFALLS.md#f7)（功能做了，没有镜头和手）。

### 阶段 7　声音

- **进入条件**：阶段 6 的站点和节奏已定（声音跟着走线和观礼的时刻）。方案可以早写。
- **产出**：每个分区的乐句、主题怎么随印出现、环境声（每一种有出处：什么地方有、什么时候没有）、脚步的地面种类、殿内外的空气。
- **必须跑**：`score.test`、`steps.test`、`mountain-air.test`、`bell.test` 一类；`tools/music.mjs` 渲十分钟的报告（峰值、静音段、乐句日志）；e2e `sound`、`music`、`mountain`。**每类新声音先出三档试听文件给所有者选**，选定的电平再写进测试。
- **评审**：音乐评审。
- **所有者拍板**：每类声音的电平和相互的远近（听了再定）；配乐多还是少。
- **退出条件**：
  1. 每种声音在 `SOURCES.md` 有一行，写着所有者选的档。
  2. 殿内外、各分区之间听得出区别，有测量（`tools/mountain-sound.mjs` 一类）。
  3. 上一关的十分钟报告与改前一致（改到 `score.js`、`audio.js` 时）。

## 附录丁　给新物件声明参数，在调试面板里拖着调（#684）

调试面板（`?debug`：开发服务器、PR 预览、canary 带 `?debug=1`）里有一组「物件」：选中一件参数化的东西，面板列出它的参数，拖动后**只重建这一件**，调好后「复制片段」得到一段按关卡自己的写法写的对象字面量，贴回关卡文件。做法学自 Polyfork（polyfork.dev：每个模型是带参数的 three.js 模块、浏览器里拖着调），只学做法，不用它的库、模型或 MCP。正式版不带这段代码（`app/src/objects-debug.js` 只在 `__DEPLOY__ !== "production"` 时被 `debug.js` 动态载入；`deploy.test.mjs` 在 production 构建里找不到它的标记 `objects-debug@684`）。面板关着、或没有 `?debug` 时不加载，也没有任何逐帧的工作：一次拖动一次重建。

**一个关卡要做的：** 在 `app/levels/<关>/debug-objects.js` 里导出 `OBJECT_KINDS(ctx)`，返回若干「种类」。引擎按 `import.meta.glob` 找这个文件，和 `hall-views.js` 一样；没有这个文件的关卡，面板里这一组只写「本关还没有登记可调的物件」。

```js
export const OBJECT_KINDS = ({ W }) => [{
  kind: "house", label: "墙外的屋",
  schema: [                                   // 每个参数一行；顺序就是片段里键的顺序
    { key: "x", type: "number", min: -300, max: 300, step: 0.01, default: 0 },   // step 的小数位也是片段保留的位数
    { key: "w", label: "宽", type: "number", min: 4, max: 15, step: 0.1, default: 7 },
    { key: "roof", label: "屋顶", type: "choice", options: ["gable", "hip", "shed"], default: "gable" },
    { key: "tone", label: "瓦色档", type: "choice", options: [{ value: 0, label: "old" }, { value: 1, label: "grey" }, { value: 2, label: "pale" }], default: 1 },
    { key: "alongX", type: "bool", default: true },
    // fmt?: (v) => string, parse?: (n) => number   数据在文件里不是字面量写法时才写，要成对：fmt 写出，parse 把算出的数换回面板的单位
    //   例：{ key: "yaw", type: "number", step: 0.5, fmt: (v) => `(${v} * Math.PI) / 180`, parse: (r) => r * 180 / Math.PI }  // 面板用度，文件用弧度
  ],
  items: () => [{ id: "7", label: "南排第 7 间" }],   // 可选的有哪些
  read: (id) => ({ x: …, w: …, … }),                 // 这一件现在的参数（只读它，不改它）
  rebuild: (id, params) => { … },                    // 按参数只重建这一件；不重建整站
  near: (x, z) => id,                                // 可选：面板上「选离他最近的」
  focus: (id) => {},                                 // 可选：选中时把镜头带过去
}];
```

`schema` 的每一项是 `{ key, label?, type: "number" | "choice" | "bool", min?, max?, step?, options?, default, fmt? }`。写法的规则（`normalize`、`toSnippet`、`parseSnippet`，在 `app/src/objects-debug.js`）：

- 数字夹在 `min`–`max` 里，按 `step` 的小数位取整；选项不在 `options` 里就拒绝；缺的键取 `default`；`schema` 里没有的键拒绝（贴错了种类）。
- 片段是一个对象字面量，键按 `schema` 的顺序：`{ x: 12.34, z: -5.6, w: 8.2, roof: "hip", tone: 2, alongX: false }`。读回时**不执行**：只认数、字符串（单双引号）、`true`/`false`、注释和结尾逗号，数的位置还认由数、`*`、`/`、括号和 `Math.PI` 组成的算式（手写的小解析，其余一概拒绝；有 `parse` 的参数，算式的结果经 `parse` 换回面板的单位）。
- 因此「参数 → 片段 → 再解析」结果相等（`tests/unit/objects-debug.test.mjs` 用一个假物件随机跑 300 组）。贴回关卡文件、把默认值改成它之后，画面应与面板里调出来的一样；**改默认外观要另开 PR、走审图**，面板只是帮你找数。

**怎么量单件重建的耗时：** 面板「重建」一行是每次拖动时 `rebuild` 本身的毫秒数，「见到效果」是到下一帧画出为止；「量重建用时」按钮用当前参数连续重建 15 次，写出中位数和最大值（控制台里同样：`__objects.time(15)` 返回 `{ n, median, max, min }`）。开发服务器（`pnpm dev`）上量，验收线是中位数 < 200 ms；量过的数写进该物件所属 PR 的说明里，带上提交号。

**T05 的接法（#684 下半，`app/levels/t05/debug-objects.js`）。** 合批的东西要单件重建，得先让它在工作台页上「各自成一块」：站点文件在面板开着的页上（`debugGate`：开发服务器、PR 预览、canary 带 `?debug=1`）给每件物件各自的 mesh、`userData.keep = true`（`mergeStatic` 认它），并设 `window.__t05Objects = { houses, figures }`；其他页（正式版、canary 不带 `?debug=1`）走原来的合批路径，一字不变，几何逐顶点相同（`tests/unit/t05-objects-debug.test.mjs`）。物件的生成函数要能「按一件、按给定参数」调用：房子是 `house(h, walls, roofs)`，造像是 `buildFigure(f, top)`（`buildAltar` 就是它的七次调用）。阴影图每个季时只画一次，所以挪了位置的物件要在重建后再 `__mood(当前季, 当前时)` 一次才会把影子画到新位置（`debug-objects.js` 的 `refresh`）。烘好的可走地面不会跟着变，调的只是画面。
