# 项目定位与调查结论（2026-11-13）

本文汇总本次与用户的一轮讨论和公开资料调查，供后续 Fable 接手时先读。
**它是调查记录，不是已批准的方案。** 用户最后说「先整理给文章，给 fable 后续参考再定」，
所以下面所有建议都还没有动代码，也不要把任何一条当成已经决定的需求。
代码现状仍以 `README.md` 和 `CLAUDE.md` 为准。

## 一、用户给出的项目设想

原话：「我对本项目的设想是游览全球的小众寺庙，一城一寺，一处净心空间」。

三层意思要分开看：

- **内容规模**：不止一座径山寺，是许多座，每座对应一座城。
- **气质**：安静、可凝视、无社交压力，不是任务、剧情或奇观。
- **产品形态**：链接即开的网页体验，不是必须安装的应用。

创意来源后来澄清：是参考韩国近期爆红的「在线拜佛」项目才有的这个想法。
**用户明确说那个项目是可以自由走动的**，所以自由行走是设想的一部分，不要擅自删掉。
用户也说过「体验优先」，一度愿意考虑不支持手机兼容，但这只是讨论中的取舍，不是已定决定。

## 二、讨论中反复出现、已经收敛的判断

### 引擎：不引入 Unity

用户先问是否需要引入 Unity 的物理碰撞系统，再问是否用独立模型提升质感。
结论是**three.js 到底，Unity 不进**：

- Unity 的碰撞不是能单独拆出来的库，调用它就得整个引入 Unity 运行时。
- 对照 `docs/LITTLEPRINCE-TEARDOWN.md`：小王子是 Unity 6000.3 WebGPU 桌面构建，
  启动三件套约 92 MB，章节包解码后约 2.11 GB，要求 BC 纹理压缩和独显，页面明确拒绝手机平板。
- 我们整个 `app/` 约 6.1 MB、零构建、推 `main` 即发布 GitHub Pages、手机优先。
  引入 Unity 会同时牺牲手机、静态发布和「一城一寺」的更新节奏。
- 画面差距的真实来源是美术资产和光照，不是引擎。继续按
  `docs/SALTLINE-TEARDOWN.md` 的启动烘焙贴图、独立背景、体积雾、软阴影路线在 three.js 里补。

### 碰撞和物理：不是当前瓶颈

纯前端物理引擎确实有，主流四个：Rapier（Rust→WASM，活跃，three.js 官方示例已收录）、
cannon-es（纯 JS 约 150 KB，基本停更）、Ammo.js（Bullet 移植，重但功能全）、
Jolt Physics.js（较新，生态薄）。**若要引，首选 `@dimforge/rapier3d-compat`**：
wasm 内嵌、异步 `await init()`、自带 `KinematicCharacterController`（贴墙滑行、自动上台阶、
贴地、坡度阈值），可把 `site.js` 已有 `walk.solids` 矩形变成固定 collider。

但三个界限要记住：

1. 物理只回答「这一步能不能走、撞了怎么滑」，不回答「隔着墙怎么绕过去」，后者是寻路（A* / 导航网格）。
2. 现有 `createWalker` 已经在做阻挡、滑动、台阶坡道和香炉绕行；引入 wasm 会增加包体和移动端负担，
   还会破坏 `walkthrough-test.js` 依赖的确定性。
3. **韩国 Sansa 没有任何物理引擎**，就是自定义矩形碰撞，照样承载单日十万访问。
   这等于用真实产品验证了「不必为自由走动引入引擎」。

最小接入路径若将来要做：vendored `rapier3d-compat` 放进 `app/v/` 一类目录，矩形 collider + 角色控制器，
保留手写 `decks`/`ramps` 高度逻辑（纯几何交给刚体反而容易抖），再补寻路，
并以 `walkthrough-test.js` 全程通过为验收。

### 独立模型：可以，但要克制

用户问能否引入 three.js 独立模型提升美术质感。结论是**模型治「近看的形」，光照与材质一致性治「整体质感」，
现在缺的主要是后者**。

- 值得做模型的：斗拱、石灯、钟鼓、香炉、茶具、佛像，都是 README 自己承认近看露怯的 focal 件。
- 不该换的：`buildHall` 参数化建筑本体。它是「加一栋建筑 = 一次 `put()`」和行走范围、
  地面暗部自动跟随的根基，也是多寺院复用的引擎。
- 边界：`buildHall` 是宋式木构生成器，不是全球寺院通用生成器；藏传、日本、东南亚、石构寺院
  需要各自的建筑词汇，这不是换引擎能解决的。
- 模型必须走 `gltf-transform optimize`：几何 `meshopt`（解码比 Draco 快），贴图 KTX2/Basis 或 webp，
  1024–2048，惰性加载并 `dispose`，重复件 `InstancedMesh`，静态几何继续 `geo.merge`。
  预算：初始下载 <10 MB、draw call <100、贴图 ≤2048。
  版权也要留意，仓库已因佛像模型要求私有。
- 优先于加模型的四件事：启动烘焙贴图替掉逐像素噪声、统一色调映射（院子 AgX、殿内 ACES 目前不一致）、
  体积雾、软阴影。环境光已有 `sky.js` 的 PMREM，不是空白。
- 最小验证：先做一个石灯走完压缩管线当模板，并顺手压一遍现有约 11 MB 佛像。

### 手机兼容：建议保留并做渐进增强

「体验优先」不等于砍手机。Sansa 的传播靠零门槛打开，手机是零门槛的一部分。
建议检测 WebGPU：桌面走高档（体积雾、软阴影、更高分辨率、甚至泼溅背景），
手机退回 WebGL2 现有三档。`quality.js` 的分档 + 帧时 governor 已是这个结构。
真正该抬体验的烘焙贴图、雾、软阴影、色调映射，桌面和手机都受益。

### 一次被纠正过的判断

我一度建议把「可走动的寺院」改成「可凝视的寺院」，理由是省掉碰撞与性能负担。
用户指出创意来源是**可自由走动**的韩国项目，这个建议因此不成立。
自由走动是本体感，Sansa 打动人靠的是「我自己走到蒲团前跪下」。
此处记录以免后续再次把行走当负担删掉。

## 三、竞品与参照项目（已上线）

### 韩国「산사 / Sansa」：最直接的创意来源

- 网址 <https://sansatemple.com>，2025 年末走红，独立开发者 @metamong.dev 用 AI 编码工具做的。
- 浏览器直接开，免安装免登录；随机给一个诗意名号，化身小沙弥，在院子与法堂里**自由走动**，
  可坐下、合掌、叩拜、拨 108 念珠、听《般若心经》和虫鸣风声。
- **刻意不做聊天**：多人同殿，可见彼此却无话可说，零社交压力。
- 报道数据：三天约 60 万访问、单日约 10 万、服务器一度挤爆，一座法堂曾同时四千多人。
  不同来源数字略有出入，用之前再核。

**技术栈是本次实际抓取线上文件核对的**（`index.html`、`assets/index-*.js`、`assets/game-*.js`）：

- Vite 打包的原生 TS，入口约 5 KB，按需分块；未见 React/Vue。
- three.js + WebGL，不是 WebGPU；有 GLTF/GLB 加载器、Meshopt 解码器、蒙皮角色。
- PBR 贴图三件套 `color/normal/roughness.jpg`，地面、粉墙、岩石、屋顶、石、木、布各一套；
  有 PMREM、`scene.environment`、`toneMapping`。
- 多人用原生 `WebSocket` + `presence`，约二十处 `.send()`，没有 socket.io、Supabase、WebRTC。
- 音频是采样 wav（木鱼等），不是全合成。
- **没有 rapier/cannon/ammo 任何物理引擎**，自由走动是自定义碰撞。

用户评价「画面太 low」。核对后判断：不是技术弱，而是美术预算与风格选择。
它有 PBR 法线贴图和环境光，但贴图偏平面、几何简单、配色灰，是刻意低多边形气质。
我们的渲染管线在程序材质、AgX、泛光、调色这层反而更讲究。
它用几乎相同的栈做到爆发，说明路线没错，差距在美术与产品层，不在引擎。

**真正该从 Sansa 搬的三样**：可见化身、几处仪式动作、沉默共处。
前两样在我们现有的机位、钟鼓、上香体系里已有胚子，成本低、对「净心」的增益比渲染升级大。

## 四、代码层面：哪些能复用，哪些绑死在径山寺

**可跨寺院复用**：`buildHall(M, opts)` 参数化营造；`materials.js` / `glsl.js` / `geo.js` /
`plaque.js` / `quality.js` / `post.js` / `app/v/`；`ground.js` / `backdrop.js` / `bamboo.js` /
`sky.js` 的接口已按 SITE/LEVELS/terrain 传参（但默认气质是竹林山寺）；`audio.js` 的合成机制；
`tools/shots.js` 按 `views` 名渲染。

**硬绑径山寺**：`site.js` 几乎全部（`SITE/LEVELS/APPROACH/terrain`、所有 `put()` 坐标与匾文、
`hall{box,door,inside}`、`strikers`、`views`、`censer/sunFocus`）；`hall.js` 的板绘标定常量
（`PLATE_W=941`、`HORIZON_Y=1004`、`FOCAL_PX=1793`）、`plate.webp`、`app/m/` 佛像；
`index.html` 文案；`yard.js` 的竹林排除区、`grove()` 阈值、进殿逻辑；`sky.js` 的 SUN_DIR/雾色；
宋式白墙深木灰瓦配色；`walkthrough-test.js` 写死的路点、98/196 Hz 钟声断言、登顶高度 20.8。

**直接复制 `app/` 建第二座寺，最先坏的是**：5.2 MB 佛像和 three.js 每寺重复一份；任何引擎修复要在 N 处重做；
路点、`hall.inside()`、`strikers` 判定全部失灵；两寺无法共享一个 `views` 与测试管线。

### 「一城一寺」内容模型（尚未实施）

每寺一份 manifest：id、寺名、匾文、`SITE/LEVELS/terrain`、建筑参数表、`views`、
殿内配置（plate + 标定常数 + 模型）、音频、配色覆盖。共享引擎放 `src/`，每寺只换清单 + 殿内资产 + 入口文案。

三个选项，约束同为「无构建、GitHub Pages、移动优先、约 6 MB、净心」：

- **A（最便宜）**：维持单应用，把 `site.js` 顶部常量、`hall.js` 标定、文案抽成一份 `temple.json`。
  引擎不动，两个工具跑通即完成，为「第二座寺 = 一个数据包」铺路。
- **B（中期推荐）**：单仓多寺，`app/temples/<id>/` 各放清单与殿内资产，共用 `src/`，
  静态 `registry.js` 按 `?temple=` 选寺。Pages 一次部署，引擎只存一份。
- **C**：每寺独立静态站。只在两寺差异大到不值得共享时才考虑，超过两座维护成本失控。

净心要求与 A/B 相容：保持慢走、无任务系统、合成环境声；学 Sansa 的「一地一声景」而非章节任务。
